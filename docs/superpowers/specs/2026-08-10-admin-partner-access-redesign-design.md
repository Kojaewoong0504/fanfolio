# Fanfolio 관리자 파트너 권한 및 반응형 UI 개편 설계

## 1. 목표

Fanfolio 관리자 웹을 선택된 2번 시안인 **파트너 디렉터리 분할 화면**을 기준으로 다시 구성한다. 루트 관리자는 계약된 기업, 기업 담당자, 담당 아티스트를 한곳에서 관리하고, 기업 담당자는 본인 회사와 배정된 아티스트 범위 안에서만 운영한다. 모든 관리자 화면은 브라우저 너비 안에 들어와야 하며 페이지 전체에 가로 스크롤이 생기지 않아야 한다.

이 작업에는 팬 앱 아이콘의 흰색 외곽 여백 제거도 포함한다. 아이콘의 카드 모티프와 남색·보라색 브랜드 색상은 유지하되, 앱 아이콘 슬롯을 가득 채우는 완성 자산으로 교체한다.

## 3. 관리자 종류와 권한 경계

기존 `User.role == admin`은 로그인 클라이언트 구분에 유지하고, 실제 운영 권한은 별도 관리자 멤버십에서 판단한다.

### 루트 관리자

- `organization_id`가 없는 전역 관리자다.
- 파트너 기업 생성·수정·중지, 기업 담당자 발급·비활성화, 기업별 아티스트 연결, 담당자별 아티스트 배정을 수행한다.
- 전체 아티스트, 카드, 카드 검수·공개, 드롭·코드, 서비스 사용자, 감사 로그를 조회하고 관리한다.
- Render의 `ADMIN_BOOTSTRAP_EMAIL`로 보장되는 초기 관리자는 자동으로 루트 멤버십을 갖는다. 초기 루트 관리자는 첫 로그인 비밀번호 강제 변경 대상이 아니다.

### 기업 담당자

- 한 계정은 정확히 한 파트너 기업에 소속된다.
- 한 담당자는 해당 기업에 연결된 아티스트 중 여러 아티스트를 배정받을 수 있다.
- 세부 역할은 `manager`, `editor`, `viewer` 세 가지다.
  - `manager`: 배정된 아티스트 정보와 카드 초안을 생성·수정하고 검수 요청까지 수행한다.
  - `editor`: 배정된 아티스트 정보와 카드 초안을 생성·수정하지만 담당자·권한은 변경하지 못한다.
  - `viewer`: 배정된 범위의 정보와 진행 상태를 읽기만 한다.
- 카드 최종 공개, 드롭·코드 발급, 기업·담당자·권한 변경은 루트 관리자만 수행한다.
- 기업 담당자는 다른 기업, 배정되지 않은 아티스트, 그 아티스트의 카드 존재 여부를 알 수 없어야 한다. 범위 밖 개별 리소스 요청은 `404`로 응답한다.

### 기본 보안 규칙

- 모든 관리자 API는 기본 거부 방식으로 서버에서 범위를 검증한다. 프론트 메뉴 숨김은 보안 수단으로 사용하지 않는다.
- 루트 전용 엔드포인트에 기업 담당자가 접근하면 `403 ADMIN_ROOT_REQUIRED`를 반환한다.
- 배정 범위 밖 리소스 조회·수정은 `404 RESOURCE_NOT_FOUND`를 반환해 ID 추측으로 존재 여부를 확인할 수 없게 한다.
- 담당자 비활성화 또는 권한 변경 시 해당 사용자의 refresh-token family와 현재 세션을 모두 폐기한다.
- 조직, 담당자, 아티스트 배정, 상태 변경은 모두 감사 로그에 조직 및 아티스트 범위와 함께 남긴다.

## 4. 데이터 모델

### `organizations`

- `id`: 문자열 기본키
- `name`: 기업명
- `slug`: 고유 식별자
- `status`: `active | suspended`
- `contact_name`, `contact_email`: 계약 담당자 정보
- `contract_starts_at`, `contract_ends_at`: 계약 기간, 선택 입력
- `logo_url`: 선택 입력
- `created_at`, `updated_at`

### `admin_memberships`

- `user_id`: `users.id` 기본키·외래키
- `organization_id`: 루트는 `NULL`, 기업 담당자는 `organizations.id`
- `access_level`: `root | manager | editor | viewer`
- `status`: `active | suspended`
- `display_name`
- `created_by_user_id`
- `last_login_at`, `created_at`, `updated_at`
- `root`는 조직이 없어야 하고 그 외 역할은 조직이 있어야 한다.

### `organization_artists`

- 복합 기본키: `organization_id`, `artist_id`
- 기업이 관리 가능한 전체 아티스트 풀을 정의한다.
- 기업에서 아티스트 연결을 해제할 때 해당 아티스트의 담당자 배정도 같은 트랜잭션에서 제거한다.

### `admin_artist_assignments`

- 복합 기본키: `admin_user_id`, `artist_id`
- `assigned_by_user_id`, `created_at`
- 담당자와 아티스트는 같은 기업에 속해야 하며, 아티스트가 먼저 `organization_artists`에 포함돼 있어야 한다.

### `audit_logs` 확장

- `organization_id`, `artist_id`를 선택 컬럼으로 추가한다.
- 기업 담당자 감사 로그는 본인 조직과 배정 아티스트에 해당하는 기록만 반환한다.

## 5. API 계약

모든 응답은 기존 공통 `{ data, meta }` 성공 형식과 공통 오류 envelope를 유지한다.

### 현재 관리자 컨텍스트

- `GET /api/admin/me`
- 반환: 사용자 기본 정보, `accessLevel`, 조직 요약, 배정 아티스트 목록, 허용 작업 목록
- 관리자 앱은 세션 복구 직후 이 응답으로 메뉴와 조직 컨텍스트를 구성한다.

### 루트 전용 파트너 관리

- `GET /api/admin/organizations?query=&status=&page=`
- `POST /api/admin/organizations`
- `GET /api/admin/organizations/{organization_id}`
- `PATCH /api/admin/organizations/{organization_id}`
- `PUT /api/admin/organizations/{organization_id}/artists` body: `{ "artistIds": [...] }`
- `GET /api/admin/organizations/{organization_id}/members`
- `POST /api/admin/organizations/{organization_id}/members` body: `{ "email", "displayName", "accessLevel", "artistIds" }`
- `PATCH /api/admin/organizations/{organization_id}/members/{user_id}` body: 역할 또는 상태
- `PUT /api/admin/organizations/{organization_id}/members/{user_id}/artists` body: `{ "artistIds": [...] }`
- 담당자 생성 응답은 기존 방식대로 임시 비밀번호를 한 번만 반환한다. 이메일 발송은 이번 범위에 포함하지 않는다.

### 기존 운영 API 범위 적용

- `dashboard`, `catalog`, `cards`, `artist-profiles`, `audit-logs`는 관리자 컨텍스트에 따라 결과를 필터링한다.
- 기업 담당자가 카드를 생성할 때 `artistId`는 필수이며 배정된 아티스트여야 한다.
- 기업 `manager`와 `editor`는 초안 생성·수정·검수 요청만 가능하다. 검수 결정, 최종 공개, 드롭·코드, 서비스 사용자 역할 변경은 루트 전용이다.
- `viewer`의 모든 변경 요청은 `403 ADMIN_WRITE_REQUIRED`를 반환한다.
- 루트 관리자는 기존 운영 기능 전체를 유지한다.

## 6. 관리자 웹 정보 구조

### 공통 셸

- 좌측 탐색에는 로고와 `개요`, `파트너`, `아티스트`, `카드`, `드롭·코드`, `서비스 사용자`, `감사 로그`를 배치한다.
- `파트너`, `서비스 사용자`는 루트에게만 표시한다.
- `드롭·코드`는 루트에게만 표시한다.
- 하단 계정 메뉴에서 현재 관리자 이름, 역할, 조직, 로그아웃을 제공한다.
- 상단에는 현재 범위 배지(`ROOT` 또는 기업명), 알림, 계정 메뉴만 둔다. 불필요한 전역 새로고침 버튼과 ‘시스템 정상’ 장식은 제거한다.
- 호스팅 환경의 API 주소나 관리자 이메일을 사용자가 직접 수정하는 설정 화면은 제거한다.

### 파트너 관리: 선택된 2번 시안

- 루트 전용이다.
- 화면은 `파트너 목록 열`과 `선택 기업 상세 영역`의 분할 구조다.
- 파트너 목록은 검색, 활성/중지 상태, 로고, 기업명, 페이지 이동을 제공한다.
- 기업 상세 헤더는 기업명, 상태, 계약 기간, 대표 담당자, 발행 카드 수, 최근 업데이트를 표시한다.
- 상세 탭은 `개요`, `관리자`, `아티스트`다.
- 관리자 탭은 이름·이메일, 역할, 배정 아티스트, 최근 로그인, 상태, 작업 메뉴를 한 행에 표시한다.
- `관리자 추가`는 오른쪽 drawer에서 처리하고, 생성 후 임시 비밀번호를 한 번만 보여준다.
- `아티스트 배정`은 선택 담당자 옆의 작은 popover/drawer에서 체크박스로 편집하고 저장한다.
- 삭제 대신 `비활성화`를 사용하고 확인 대화상자를 제공한다.

### 카드 관리

- 현재의 한 줄짜리 초대형 등록 폼을 제거한다.
- 기본 화면은 검색, 상태 필터, 아티스트 필터, 카드 목록, `카드 등록` 버튼으로 구성한다.
- `카드 등록`은 오른쪽 drawer를 열어 이미지, 카드명, 시즌, 아티스트, 멤버, 등급, 발행 수량을 단계적으로 입력한다.
- 기업 담당자에게는 배정된 아티스트와 멤버만 선택지로 제공한다.
- 900px 이하에서는 표를 카드형 목록으로 바꾸고 핵심 필드와 작업 메뉴만 유지한다.

### 개요·아티스트·감사 로그

- 개요의 지표는 루트면 전체, 기업 담당자면 배정 범위만 집계한다.
- 아티스트 화면은 회사와 담당자 배정을 드러내며, 기업 담당자는 배정된 아티스트 정보만 편집한다.
- 감사 로그는 검색·행동 필터를 유지하되, 루트는 전체, 기업 담당자는 허용 범위만 본다.

## 7. 반응형 규칙

- `1280px 이상`: 208px 좌측 탐색 + 280px 파트너 목록 + 유동 상세 영역
- `1024~1279px`: 72px 아이콘 탐색 + 240px 파트너 목록 + 유동 상세 영역
- `768~1023px`: 탐색은 접히는 drawer, 파트너 목록은 상단 선택 패널, 상세가 전체 너비를 사용한다.
- `767px 이하`: 관리자 웹의 핵심 조회와 간단한 상태 변경만 지원하며, 표는 세로 카드 목록으로 전환한다. 복잡한 권한 배정은 전체 화면 sheet를 사용한다.
- 모든 `input`, `select`, `button`, `table` 컨테이너에 `min-width: 0`을 적용하고, 페이지 루트에 `overflow-x: clip`을 적용한다. 내부 텍스트는 줄바꿈 또는 말줄임으로 처리한다.
- 1024, 1280, 1440px 화면에서 문서 전체 `scrollWidth <= clientWidth`를 자동 검증한다.

## 8. 팬 앱 아이콘

- 현재 카드 페이지 모티프와 남색·보라·분홍 팔레트는 유지한다.
- 현재 PNG에 포함된 흰색 바깥 캔버스와 과도한 여백을 제거한다.
- 원본 앱 아이콘은 1024 × 1024 RGB PNG로 생성하고 아트워크가 캔버스 전체를 채우게 한다.
- `apple-touch-icon.png` 180 × 180, `favicon.png` 64 × 64, PWA용 192 × 192 및 512 × 512를 원본에서 리샘플링한다.
- 작은 favicon에서는 세부 레이어가 뭉개지지 않도록 단순화된 동일 모티프를 사용한다.
- 이미지 자산은 Image Gen으로 만들고 실제 크기에서 가장자리 흰색 halo가 없는지 확인한다.

## 9. 오류·빈 상태

- 파트너가 없으면 설명과 `첫 파트너 등록` 버튼을 제공한다.
- 담당자가 없으면 `관리자 추가`를 주 행동으로 제시한다.
- 아티스트 배정이 없으면 기업 담당자는 다른 운영 메뉴보다 먼저 ‘담당 아티스트가 아직 배정되지 않았습니다’ 안내를 본다.
- API `401`은 한 번의 refresh 회전 후 로그인 화면으로 보낸다.
- `403`은 역할에 맞는 권한 안내, `404`는 일반적인 ‘항목을 찾을 수 없음’, `409`는 중복 이메일·slug·잘못된 배정 관계를 구체적으로 표시한다.
- drawer 저장 중에는 버튼을 비활성화하고 성공 후 목록과 상세를 같은 데이터로 다시 동기화한다.

## 10. 테스트와 완료 조건

### 백엔드 계약 테스트

- bootstrap 관리자는 root 컨텍스트를 받는다.
- root만 기업과 기업 담당자를 생성·수정·비활성화할 수 있다.
- 한 기업 담당자는 한 기업에만 속하고 여러 아티스트를 배정받을 수 있다.
- 다른 기업 또는 미배정 아티스트의 카드·프로필을 조회하거나 수정할 수 없다.
- manager/editor/viewer별 쓰기 권한이 서버에서 거부·허용된다.
- 담당자 비활성화와 역할 변경 시 기존 refresh 세션이 폐기된다.
- 조직·담당자·아티스트 배정 변경이 범위 정보와 함께 감사 로그에 남는다.
- 기존 루트 관리자 카드·드롭·코드 계약 테스트는 계속 통과한다.

### 관리자 프론트 테스트

- root와 기업 담당자별 탐색 항목이 올바르게 달라진다.
- 파트너 선택, 관리자 추가 drawer, 아티스트 배정, 비활성화 흐름이 동작한다.
- 카드 등록이 drawer에서 수행되고 기업 담당자의 선택지가 배정 범위로 제한된다.
- 1024, 1280, 1440px에서 페이지 가로 overflow가 없다.
- 768px에서 표가 카드형 목록으로 전환되고 주요 작업이 키보드로 가능하다.

### 시각 QA

- 선택 시안과 동일한 1440 × 1024 상태를 캡처해 전체 레이아웃, 타이포그래피, 색상, 간격, 아이콘, 실제 데이터 표현을 비교한다.
- 현재 문제 화면과 새 화면을 같은 뷰포트에서 비교하고, P0/P1/P2 차이가 없어질 때까지 수정한다.
- `design-qa.md`의 최종 결과가 정확히 `passed`여야 한다.

### 배포 완료 조건

- Alembic migration이 기존 데이터 삭제 없이 적용된다.
- 백엔드 pytest, Ruff, 관리자 Node 테스트, 팬 앱 테스트·lint·build가 모두 성공한다.
- 변경 사항을 GitHub `main`에 push하고 Render migration/API 및 Vercel 관리자·팬 앱 배포 상태를 확인한다.
- 배포된 관리자에서 루트 로그인, 파트너 생성, 담당자 생성, 아티스트 배정, 범위 제한을 실제 브라우저로 smoke test한다.

## 11. 이번 범위에서 제외

- 담당자 초대 이메일 자동 발송
- 한 담당자의 여러 기업 동시 소속
- 기업 담당자가 다른 기업 담당자를 직접 초대하는 기능
- 계약·청구·정산 기능
- 세부 필드 단위 커스텀 권한 편집기
- 기업 담당자의 드롭·QR 코드 직접 발급
