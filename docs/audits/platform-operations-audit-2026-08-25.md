# Fanfolio 제품·운영 준비도 감사

- 작성일: 2026-08-25
- 범위: 팬앱, 관리자 웹, 아티스트 스튜디오, 공용 FastAPI 백엔드
- 목적: 현재 기능 범위와 데이터 연결 상태를 정리하고, 실제 운영을 위해 필요한 다음 작업의 우선순위를 정한다.

## 1. 전체 판단

Fanfolio는 단순 UI 프리뷰를 넘어 팬 수집·성장·거래·상점·소셜 기능과 운영 API가 연결된 제품 단계에 있다. 다만 기능의 존재와 실제 서비스 운영 준비는 구분해야 한다.

| 영역 | 준비도 판단 | 현재 상태 |
| --- | --- | --- |
| 팬앱 기능 범위 | 높음 | 주요 사용자 흐름 대부분 구현 |
| 데이터·API 연결 | 높음 | 수집·성장·거래·상점·알림 API 연결 |
| 팬앱 UI/UX | 보통 | 공통 셸은 안정됐지만 빈 상태와 세부 화면 회귀 위험 존재 |
| 관리자 웹 | 보통 | 관리 기능은 넓지만 통합 관제·CS 기능 부족 |
| 아티스트 스튜디오 | 보통 | 제작·미리보기·심사 제출 가능, 협업·버전 기능 부족 |
| 운영 출시 준비 | 낮음~보통 | 다중 사용자 E2E, 신고·분쟁·개인정보·관제 검증 필요 |

## 2. 제품 및 서버 구성

세 프론트엔드는 같은 저장소에 있지만 서로 독립된 애플리케이션이다.

| 제품 | 디렉터리 | 로컬 주소 | 배포 단위 |
| --- | --- | --- | --- |
| 팬앱 | `frontend` | `http://localhost:5173` | `fanfolio-fan` |
| 관리자 웹 | `admin_app` | `http://localhost:4174` | `fanfolio-admin` |
| 아티스트 스튜디오 | `builder_app` | `http://localhost:4175` | `fanfolio-studio` |
| 공용 API | `backend` | 기본 `http://localhost:8000` | 별도 FastAPI 서버 |

관리자 웹과 아티스트 스튜디오는 서로 다른 프론트 서버다. 다만 완전히 분리된 백엔드를 각각 가지는 구조는 아니며, 팬앱을 포함한 세 앱이 동일한 FastAPI API와 데이터베이스를 사용한다. 인증 방식과 권한 범위는 제품별로 분리한다.

## 3. 현재 구현된 핵심 기능

### 팬앱

- 이메일·소셜 로그인, 비밀번호 변경·초기화
- 홈, 탐색, 아티스트·팬 검색
- 카드 등록, 보관함, 카드팩, 위시리스트, 수집 목표
- 팬 프로필, 공개 컬렉션, 팔로우
- 거래 제안·수락·거절·취소
- 미션, XP, 팬 레벨, 시즌 패스, 보상
- 이벤트 조회·신청·댓글
- 상점, 상품 상세, 포인트 결제, 구매 내역, 환불
- 인앱 알림과 실시간 알림 스트림

### 관리자 웹

- 카드·카드팩·발급 배치·인증번호 운영
- 상품 등록, 상세 콘텐츠 블록, 모바일·데스크톱 미리보기
- 미션·업적·레벨 정책·보상·패스·컬렉션 캠페인 관리
- 관리자·파트너·아티스트 계정과 권한 관리
- 카드 심사·승인·공개
- 감사 로그, 운영 통계, 내보내기

### 아티스트 스튜디오

- 카드 초안 작성·수정
- 이미지·영상·음성·손글씨 자산 등록
- 효과 미리보기와 배경 제거 작업
- 심사 준비도 확인과 검수 요청
- 기본 인사이트 조회

## 4. 데이터 무결성과 결제 범위

PG는 아직 범위에서 제외한다. 자체 포인트 경제에서는 다음 항목이 구현되어 있다.

- 포인트 조정의 멱등성
- 포인트 결제와 주문 생성의 단일 트랜잭션 처리
- 사용 전 주문의 원자적 환불
- 카드팩 사용권 및 보상 지급
- 중복 환불·중복 지급 방지

사업자·PG 준비 이후에는 실제 승인·취소, 결제사 대사, 현금성 환불 정책을 별도 수직 기능으로 추가해야 한다.

## 5. 운영 전 우선 해결 항목

### P0. 출시 안정성

1. 두 사용자 거래 전체 E2E
   - 제안 → 카드 잠금 → 수락·거절 → 소유권 이전 → 알림 → 내역 반영
   - 동시 수락, 동일 카드 중복 거래, 연결 중단 후 재시도 검증
2. 관리자 UI 실제 mutation E2E
   - 이미지 업로드 → 카드·상품 생성 → 심사 → 공개 → 팬앱 노출
3. 운영 인프라 검증
   - PostgreSQL, Redis, SMTP, 작업 큐, 비밀키, 백업·복원 훈련, 장애 알림
4. 운영 안전 기능
   - 신고, 차단, 숨김, 거래 분쟁, 관리자 조치, 사용자 통지
5. 개인정보 자기관리
   - 계정 삭제, 개인정보 다운로드, 동의 이력

### P1. 운영 경험

1. 푸시 알림과 기기 토큰 관리
2. 빈 화면에 대한 초기 운영 콘텐츠와 행동 유도
3. 실패 작업·환불·보상·거래 상태를 모아보는 운영 관제
4. 360px·390px·430px 공통 화면 회귀 테스트
5. 키보드 접근성, 포커스, 대비, 스크린리더 라벨 검증

## 6. 관리자 웹 다음 기능

1. **운영 관제 대시보드**
   - 실패한 결제·환불·보상·카드팩 개봉·거래 작업 조회와 재처리
2. **팬 360도 화면**
   - 계정, 카드, 포인트 원장, 거래, 주문, 신고, 제재, 문의 타임라인
3. **CS·분쟁 처리함**
   - 담당자 배정, 증거 확인, 거래 정지, 환불·보상, 답변 기록
4. **상품 운영 고도화**
   - 재고, 판매 기간, 사용자별 제한, 예약 공개, 노출 위치, 팬 세그먼트
5. **이중 승인**
   - 대량 포인트 지급, 환불, 상품 공개, 확률 변경의 작성·승인 분리
6. **분석 고도화**
   - 유입→수집→거래→구매 전환, 코호트 잔존율, 아티스트별 활성 팬

## 7. 아티스트 스튜디오 다음 기능

1. 자동 저장과 연결 중단 후 복구
2. 버전 이력, 변경 비교, 이전 버전 복원
3. 카드·콘텐츠 영역별 댓글과 협업
4. 카드·뉴스·이벤트·상품 공개 일정 캘린더
5. 승인 자산·템플릿·브랜드 키트 라이브러리
6. 팬앱과 동일한 실제 기기 폭 미리보기
7. 제출→수정 요청→재제출→승인 상태와 반려 사유 표시
8. 개인정보를 침해하지 않는 수집·반응·콘텐츠 비교 인사이트

## 8. UI/UX 발전 원칙

화면별 CSS를 개별 수정하는 대신 다음 세 가지 화면 계약을 고정한다.

1. **루트 탭 화면**: 로고, 알림, 프로필, 동일 하단 탭
2. **세부 화면**: 동일한 뒤로가기, 제목, 보조 문구, 콘텐츠 시작 위치
3. **몰입형 플로우**: 카드 등록·결제·거래의 단계 표시와 고정 하단 버튼

공통 계약별 자동 스크린샷을 360px·390px·430px에서 생성해 상단 위치, 좌우 여백, 하단 탭, 스크롤바 회귀를 차단한다.

## 9. 권장 실행 순서

1. 두 계정 거래 E2E와 운영 인프라·백업 복원 검증
2. 신고·차단·분쟁·CS·실패 작업 관제 구현
3. 관리자 예약 공개·노출 관리와 스튜디오 버전·협업·캘린더 연결
4. 푸시 알림, 코호트 분석, 팬 세그먼트, 개인화 추천 추가

## 10. 증거·추론·미확인 범위

### 확인된 증거

- 팬앱 주요 라우트와 API 연결
- 관리자 상품 상세 콘텐츠의 팬앱 노출
- 포인트 결제·환불·보상 지급의 트랜잭션·멱등성 구현
- 관리자 카드·상품·권한·통계 기능과 스튜디오 제작·심사 기능의 코드 존재
- 현재 팬앱 루트 화면의 공통 셸과 하단 탭 표시

### 제품 판단

- 다음 투자는 팬 기능의 양적 추가보다 운영 안정성, 관리자 관제, 스튜디오 협업에 집중하는 것이 효과적이다.
- 현재 가장 큰 UX 문제는 기능 부재보다는 콘텐츠가 없는 상태가 화면 대부분을 차지하는 점과 공통 화면 계약의 회귀 위험이다.

### 미확인 또는 추가 검증 필요

- 실제 운영 환경의 PostgreSQL·Redis·SMTP·백업 복원
- 두 사용자 동시 거래와 경쟁 조건
- 관리자 이미지 업로드부터 팬앱 공개까지의 최신 브라우저 연속 흐름
- 다중 실제 기기 QR·카메라 호환성
- 관리자 웹과 아티스트 스튜디오의 최신 실행 화면 시각 회귀
