# 관리자 카드팩 발매·인증번호 운영 복구 설계

## 목표

관리자 웹의 카드 하위 메뉴에서 카드팩 생성·구성·공개와 한정 카드 발급 배치를 실제 서비스 데이터로 운영할 수 있게 한다. 기존 `card-operations` 프리뷰에서 합의한 정보 구조를 정식 화면에 적용하고, 루트 관리자에게 숨겨진 발급·인증번호 기능을 복구한다.

## 현재 문제

1. 루트 관리자는 `codes:manage` 권한을 받지만 정식 관리자 UI는 `codes:read`와 `codes:write`를 검사한다. 그 결과 루트 관리자에게 `발급·인증번호` 메뉴와 생성 기능이 숨겨진다.
2. 완성도 높은 발급·인증번호 및 배치 생성 화면은 `?preview=card-operations` 전용이다. 정식 화면은 오래된 드롭·코드 배치 UI를 사용한다.
3. 카드팩은 공개 상태와 확률만 관리하며 총 발매량, 발매 기간, 판매 상태를 표현하지 못한다.
4. 한정 특전 카드의 사전 인증번호 생성과 랜덤 카드팩의 개봉 시점 발급이 UI에서 명확하게 분리되지 않는다.

## 접근 방식 검토

### A. 프론트에서 루트 권한만 예외 처리

가장 빠르지만 권한 의미가 프론트와 백엔드에 중복되고 다른 화면에서 같은 문제가 재발한다.

### B. 기존 배치 화면만 노출

기능은 복구되지만 승인된 프리뷰의 정보 구조와 생성 흐름을 활용하지 못하고 카드팩 발매 정책도 해결하지 못한다.

### C. 권한 계약 정상화와 정식 운영 화면 통합

백엔드가 실제 세부 권한을 반환하도록 고치고, 프리뷰의 정보 구조를 기존 API에 연결한다. 카드팩에는 별도 발매 정책을 추가한다. 변경 범위는 더 크지만 권한·데이터·화면이 하나의 계약을 사용한다.

**선택: C.** 임시 예외를 추가하지 않고 실제 서비스 계약을 바로잡는다.

## 권한 설계

- 루트 관리자는 기존 `codes:manage`와 함께 `codes:read`, `codes:write`를 가진다.
- 파트너 관리자 권한은 현재의 `codes:read`/`codes:write` 범위를 유지한다.
- 관리자 메뉴와 버튼은 API가 반환한 세부 권한만 검사한다.
- 백엔드의 루트 우회 검사는 유지하되, 프론트 표시와 API 호출 가능 여부가 일치하도록 한다.

## 카드팩 발매 정책

카드팩 정의와 카드팩 발매를 분리한다.

- 카드팩 정의: 이름, 시즌/앨범, 이미지, 버전, 포함 카드, 공개 확률
- 발매 정책:
  - `unlimited`: 총량 제한 없이 개봉 시 고유 발급번호 생성
  - `limited`: 관리자가 총 발매량을 설정하고 잔여 수량을 원자적으로 차감
- 공통 필드: 발매 시작일, 종료일, 발매 상태(`draft`, `scheduled`, `active`, `sold_out`, `ended`)
- 공개된 확률 구성은 변경하지 않는다. 변경이 필요하면 새 카드팩 버전을 만든다.
- 한정 카드 인증번호 배치와 카드팩 발매량은 별개다. 전자는 카드별 코드를 사전 생성하고, 후자는 카드팩 개봉 가능 횟수를 제한한다.

## 관리자 화면

### 카드 하위 메뉴

1. 카드 관리
2. 카드팩 관리
3. 발급·인증번호

### 카드팩 관리

- 카드팩 목록과 상세에 구성 상태, 공개 상태, 발매 상태, 총량/잔여량을 표시한다.
- `새 카드팩 만들기`는 기본 정보 등록 후 카드 구성 편집으로 이동한다.
- 확률 합계가 100%인 초안만 공개할 수 있다.
- 공개 이후 `발매 설정`에서 무제한/한정, 수량, 기간을 설정한다.
- 한정 발매는 발매 전 총량 수정이 가능하지만 첫 개봉 이후 증액만 허용한다. 감소는 허용하지 않는다.

### 발급·인증번호

- 프리뷰에서 합의한 통계 카드, 검색·필터, 배치 테이블, 하단 상세 구조를 정식 화면에 적용한다.
- `추가 발급 배치 만들기`는 별도 생성 화면으로 이동한다.
- 한정 특전은 생성 수량만큼 고유 인증번호를 즉시 사전 생성한다.
- 카드팩 랜덤 발급은 인증번호를 미리 생성하지 않고 실제 개봉 순간 생성한다.
- CSV와 QR ZIP 내보내기는 기존 API를 사용한다.

## 데이터와 API

- 카드팩에 발매 방식, 총량, 개봉 수, 시작/종료일, 발매 상태를 저장한다.
- 카드팩 공개 API와 발매 설정 API를 분리한다.
- 카드팩 개봉은 한정 발매일 때 조건부 원자 갱신으로 잔여량을 확보한 뒤 결과를 만든다.
- 동시 마지막 수량 요청에서 한 요청만 성공해야 한다.
- 기존 카드팩은 마이그레이션 후 `unlimited`로 간주해 동작을 보존한다.
- 기존 코드 배치 API와 CSV/QR API 계약은 유지한다.

## 오류 처리

- 미공개 카드팩 발매 시도: 409
- 확률 합계가 100%가 아닌 카드팩 공개 시도: 409
- 발매 기간 전/후 개봉: 409
- 한정 수량 소진: 409, 발매 상태를 `sold_out`으로 표시
- 공개 후 확률 수정: 409
- 권한 부족: 403이며 UI에서는 해당 작업 버튼을 숨긴다.

## 테스트

1. 루트 관리자 응답에 `codes:read`와 `codes:write`가 포함되고 메뉴가 노출된다.
2. 파트너 역할별 읽기/쓰기 제한이 유지된다.
3. 카드팩 공개 전 확률 검증과 공개 후 구성 잠금이 동작한다.
4. 무제한 카드팩은 기존처럼 계속 개봉할 수 있다.
5. 한정 카드팩은 총량만큼만 개봉되며 동시성 경쟁에서도 초과 발급되지 않는다.
6. 한정 카드 배치는 요청한 수량만큼 중복 없는 인증번호를 만든다.
7. 정식 관리자 화면에서 배치 생성, 검색·필터, 상세, CSV/QR 내보내기가 실제 API와 동작한다.

## 구현 순서

1. 권한 회귀 테스트와 루트 권한 계약 수정
2. 카드팩 발매 데이터 모델·스키마·마이그레이션
3. 발매 설정·개봉 제한 백엔드 API와 동시성 테스트
4. 정식 카드팩 관리 화면에 발매 설정 연결
5. 프리뷰 발급 UI를 정식 배치 API에 연결
6. 백엔드·관리자 단위 테스트, 빌드, 실제 브라우저 시나리오 검증

## 완료 기준

루트 관리자와 권한 있는 파트너 관리자가 정식 관리자 웹에서 카드팩을 생성·구성·공개하고 발매 정책을 설정할 수 있다. 한정 카드는 지정 수량의 인증번호 배치를 생성할 수 있고, 랜덤 카드팩은 설정된 발매 정책에 따라 팬앱에서 개봉되며 수량·기간·확률 규칙을 위반하지 않는다.
