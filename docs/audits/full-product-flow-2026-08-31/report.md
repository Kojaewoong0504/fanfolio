# Fanfolio 전체 제품 흐름 감사

- 감사일: 2026-08-31
- 범위: 운영 관리자 웹, 아티스트 스튜디오, 팬앱 모바일
- 방식: 격리된 최신 마이그레이션 DB에서 세 역할로 로그인해 실제 생성·등록·재조회 흐름을 순회하고, 화면 증거를 코드·API·DB 상태와 대조
- 화면 증거: 이 문서와 같은 폴더의 PNG 71개

## 결론

Fanfolio는 이미 세 개의 제품이 각각 따로 보이는 수준을 넘어, **아티스트가 만든 초안이 관리자 카드 목록에 들어오고 팬의 카드 등록이 소유권·감사 데이터에 반영되는 기본 연결 구조**까지 갖췄다. 특히 아티스트 스튜디오의 레시피 기반 제작, 팬앱의 QR/코드 등록과 카드 공개 연출, 관리자 웹의 파트너 준비 체크리스트는 제품의 좋은 기준점이다.

현재 완성도를 가장 크게 깎는 것은 기능 수가 아니라 **흐름 사이의 인수인계와 상태 일관성**이다. 동일한 카드를 두고 팬 홈·탐색·아티스트 홈·개인 보관함이 서로 다른 결과를 보여주며, 카드 등록 직후 보상은 `+100 XP`로 안내되지만 백엔드는 30 XP를 적립하고 화면은 0 XP에 머문다. 또 일부 중요 화면이 브라우저 기본 폼으로 무너져 신뢰도를 떨어뜨린다.

출시 전 우선순위는 다음과 같다.

1. 카드 등록 보상 계약과 비동기 반영 방식을 하나로 맞춘다.
2. 아티스트 공개 카드와 팬 개인 보관함의 라우팅·데이터 소스를 분리한다.
3. 고객 문의, 스튜디오 협업, 설정 체크박스처럼 스타일이 무너진 운영 핵심 폼을 복구한다.
4. 모든 상세 화면의 스크롤·이미지·새로고침 상태를 공통 규칙으로 정리한다.
5. 아티스트 제작부터 팬 공개 이후 분석까지 이어지는 하나의 릴리스 워크스페이스를 만든다.

## 가장 잘 된 흐름

### 아티스트 스튜디오 제작

레시피 선택 → 미디어 준비 → 카드 정보 → 팬 화면 미리보기 → 검수 준비도 순서가 자연스럽다. 이번 감사에서 음성 카드 `오로라 보이스 메시지` 초안을 만들었고, 음성 파일이 없는 상태를 7/8 준비도로 정확히 막았다. 사용자는 왜 검수 요청을 할 수 없는지 이해할 수 있다.

![아티스트 스튜디오 검수 준비도](./25-studio-review-readiness.png)

### 팬 카드 등록과 공개

QR 촬영, 사진에서 QR 읽기, 코드 직접 입력을 한 흐름에서 제공하고, 등록 성공 뒤 카드 공개·컬렉션 이동까지 감정적 보상이 잘 설계돼 있다. 대체 경로가 명확하고 진행 단계도 이해하기 쉽다.

![팬 카드 등록 완료](./45-fan-card-register-complete-mobile.png)

### 관리자 파트너 준비 체크리스트

파트너 설정 화면은 준비 상태, 누락 항목, 다음 행동을 한곳에서 알려 준다. 이 패턴을 이벤트·팬 성장·상점·카드팩의 빈 상태에도 재사용하면 관리자 학습 비용을 크게 줄일 수 있다.

![관리자 파트너 화면](./15-admin-partners.png)

## 우선순위별 문제

### P0 — 출시 전 반드시 해결

#### 1. 카드 등록 보상이 세 가지 값으로 갈린다

- 팬 공개 화면과 완료 화면은 첫 카드 보상을 `+100 XP`라고 안내한다.
- 실제 `card_collected` 기본 보상은 백엔드에서 30 XP로 처리된다.
- 실제 감사 DB에는 XP 원장 30과 팬 레벨 총 XP 30이 기록됐지만, 팬 레벨 화면은 계속 0 XP를 표시했다.
- 원인은 등록 API 응답 직후 비동기 성장 이벤트가 끝나기 전에 진행도를 재조회하는 경쟁 상태와, 같은 사용자·아티스트 요청 키를 다시 조회하지 않는 캐시 가드가 결합된 것이다.

이 문제는 단순 표시 오류가 아니라 보상 약속과 원장의 불일치다. 보상 금액을 서버의 단일 정책 값으로 내려주고, 이벤트 처리 완료를 폴링·푸시하거나 낙관적 표시 후 서버 확정값으로 반드시 재동기화해야 한다.

![등록 화면의 100 XP 약속](./45-fan-card-register-complete-mobile.png)

![등록 후 0 XP 상태](./49-fan-level-mobile.png)

코드 근거:

- `frontend/src/App.tsx`는 첫 카드에 `+100 XP`를 하드코딩한다.
- `backend/app/services.py`의 `base_xp_for(card_collected)`는 30을 반환한다.
- 등록 완료 콜백은 비동기 작업과 경쟁하는 즉시 재조회를 수행한다.

#### 2. 팬 고객센터 문의 폼이 브라우저 기본 UI로 무너진다

FAQ 화면은 정상인데 문의하기로 전환하면 select, input, textarea, 제출 버튼이 겹치고 기본 스타일로 렌더링된다. 모바일에서 문의를 실제로 작성하기 어렵다. 컴포넌트는 존재하지만 `.settings-support-form`과 자식 컨트롤 스타일이 정의돼 있지 않다.

![무너진 고객센터 문의 폼](./59-fan-support-inquiry-mobile.png)

### P1 — 핵심 여정과 신뢰를 훼손

#### 3. 아티스트 홈의 카드 탭이 아티스트 카드가 아니라 내 보관함으로 이동한다

아티스트 홈에서 `카드` 탭 또는 `전체 보기`를 누르면 `/collection/cards` 성격의 개인 보관함으로 이동한다. 상단에는 드림스케이프 카드 컬렉션처럼 보이지만 뒤로가기 문맥도 보관함이며, 공개 카탈로그가 아니다. 코드에서도 `cards` 탭이 `onOpenCollection()`을 직접 호출한다.

아티스트 공개 카탈로그 경로를 별도로 만들고, 개인 소유 여부는 그 화면의 필터나 상태로만 보여줘야 한다.

![아티스트 카드 탭에서 열린 개인 보관함](./64-fan-artist-cards-mobile.png)

#### 4. 같은 공개 카드가 화면에 따라 존재하거나 사라진다

팬 홈과 탐색에는 공개된 드림스케이프 카드가 보이지만, 아티스트 홈은 `공개된 카드가 없어요`라고 표시한다. 아티스트 홈은 카드팩에 포함된 카드만 읽는 반면 다른 화면은 공개 카드 카탈로그를 읽기 때문이다. 공개 카드의 기준 소스를 하나로 만들거나, `카드팩에 포함된 카드`라고 정확히 이름을 바꿔야 한다.

![공개 카드를 찾지 못하는 아티스트 홈](./63-fan-artist-home-mobile.png)

#### 5. 상세 화면 진입 시 이전 스크롤 위치가 이어진다

등록 완료 뒤 보관함에 들어가면 페이지 중간부터 보이고, 카드를 열면 카드 상세도 획득 기록 영역부터 시작한다. 라우팅 유틸 일부에는 `window.scrollTo(0, 0)`이 있지만, 상태 기반 `pushState` 경로와 고정 상세 컨테이너에 일관되게 적용되지 않는다.

모든 라우트 수준 상세 화면에 `scroll restoration` 규칙을 만들고, 브라우저 뒤로가기는 이전 목록 위치를 복원하되 새 상세 진입은 반드시 자신의 최상단에서 시작해야 한다.

![중간 위치에서 열린 보관함](./47-fan-collection-card-mobile.png)

![획득 기록부터 열린 카드 상세](./48-fan-card-detail-mobile.png)

#### 6. 카드 이미지가 등록 확인·아티스트 카드 목록에서 깨진다

등록 확인 3단계에서는 이미지 대신 alt 텍스트가 카드 프레임 안에 겹치고, 아티스트 카드 목록에서도 동일한 종류의 깨진 이미지가 보인다. 성공 화면에서는 별도의 시각 fallback이 작동하므로 화면마다 이미지 해석 경로가 다르다. 인증 이미지 URL, 상대 URL 변환, fallback을 공통 카드 이미지 컴포넌트로 통합해야 한다.

![이미지가 깨진 카드 등록 확인](./44-fan-card-register-confirm-mobile.png)

#### 7. 아티스트 스튜디오 협업·설정 컨트롤이 제품 UI에서 이탈한다

협업 코멘트의 textarea, 멘션 input, 버튼과 설정의 이메일 알림 체크박스가 브라우저 기본 UI처럼 보인다. 스튜디오의 나머지 제작 경험이 좋은 만큼 이 두 화면의 이탈이 더 크게 느껴진다. 스타일 누락뿐 아니라 멘션 대상은 운영자 ID 직접 입력 대신 검색 가능한 사람 선택기로 바꾸는 편이 안전하다.

![스타일이 무너진 협업 코멘트](./26-studio-collaboration.png)

![과도하게 큰 설정 체크박스](./28-studio-settings.png)

#### 8. 아티스트 초안은 관리자에 들어오지만 하나의 릴리스 상태가 보이지 않는다

스튜디오에서 만든 `오로라 보이스 메시지`는 관리자 전체 카드 목록에 즉시 3번째 초안으로 나타났다. 연결 자체는 성공이다. 그러나 스튜디오의 7/8 준비도, 검수 요청 여부, 관리자 담당자, 수정 이력, 예정 공개 위치를 한 타임라인에서 볼 수 없다. 현재는 양쪽 제품이 같은 카드 레코드를 보더라도 사용자는 어디에서 무엇을 해야 하는지 직접 추론해야 한다.

![스튜디오 초안이 반영된 관리자 카드 목록](./66-crossapp-studio-draft-admin.png)

### P2 — 사용성을 크게 높일 개선

#### 9. 원하는 카드가 이미 보유한 카드로 제한된다

현재 화면은 `보유한 카드만 원하는 카드로 등록할 수 있어요`라고 안내한다. 거래에서 원하는 카드는 보통 아직 소유하지 않은 카드이므로 개념이 뒤집혀 있다. 실제 화면에는 카드가 하나 보이는데 선택 수는 0장으로 표시되는 상태도 확인됐다.

다음 세 개를 분리해야 한다.

- 관심 카드: 콘텐츠 저장
- 원하는 카드: 미보유 카탈로그에서 거래 수요 표시
- 내놓을 카드: 내가 소유하고 교환 가능한 카드

![소유 카드만 선택하게 하는 원하는 카드 화면](./65-fan-wanted-cards-mobile.png)

#### 10. 팬 추천은 알고리즘이 아니라 전체 팬 목록의 클라이언트 필터다

백엔드 `/fans`는 자신과 차단 사용자를 제외한 팬을 닉네임·이메일·ID 순으로 반환하고, 프런트가 같은 아티스트·교환 가능·위시리스트·신규 필터를 적용한다. 점수, 다양성, 최근성 감쇠, 안전도, 노출 제어가 없다. 이번 상태에서는 다른 시드 팬이 있어도 같은 아티스트 필터 결과가 0명이었고, 이유나 대체 추천도 제공되지 않았다.

초기에는 복잡한 ML보다 규칙 기반 점수화가 적절하다.

- 같은 아티스트·멤버 선호
- 내가 원하는 카드를 상대가 보유
- 상대가 원하는 카드를 내가 보유
- 최근 활동과 공개 컬렉션 품질
- 이미 팔로우·차단·신고 관계 제외
- 같은 사람 반복 노출 감쇠와 신규 팬 탐색 비율

각 카드에 `왜 추천했는지` 이유를 한 줄로 보여주고, 결과가 없으면 다음으로 가까운 조건을 자동 제안해야 한다.

#### 11. 관리자 빈 상태가 선행 조건을 알려주지 않는다

카드팩, 발급 코드, 상점 상품, 이벤트, 팬 성장은 각각 강한 기능이지만 첫 화면에서 무엇을 먼저 만들어야 하는지 모호하다. 특히 팬 성장 화면에는 보상·미션·레벨 패스·정책의 여러 CTA가 동등하게 나타난다.

파트너 화면의 준비 체크리스트 패턴을 재사용해 `조직/아티스트 → 카드/보상 → 노출/일정 → 검수/공개` 순서와 누락 조건을 보여줘야 한다. 각 실패 메시지는 관련 설정으로 바로 이동해야 한다.

![선행 순서가 모호한 팬 성장 운영](./09-admin-growth.png)

#### 12. 일부 빈 상태가 로딩 실패처럼 보인다

팬 홈의 이벤트가 없을 때 큰 어두운 배너와 작은 `이벤트 둘러보기`만 남는다. 이미지가 늦게 로딩되는 상황과 시각적으로 구분되지 않는다. `현재 진행 중인 이벤트가 없어요` 같은 명시적 제목, 다음 예정, 알림 받기 또는 과거 이벤트 보기를 제공해야 한다.

#### 13. 프로필 편집과 알림 탭에 작은 모바일 레이아웃 결함이 남아 있다

- 390px 뷰포트에서 프로필 편집 컨테이너는 8px, 일부 내부 래퍼는 최대 30px 가로 overflow가 측정됐다.
- 알림의 3개 탭은 2열 그리드라서 `읽지 않음`만 다음 줄로 내려간다.
- 온보딩 단계 전환 때 텍스트가 잠깐 왼쪽에서 잘리는 프레임이 재현됐다.

이들은 공통 모바일 회귀 테스트에 320/360/390/430px 폭과 화면 전환 직후 프레임을 포함해야 해결 상태를 유지할 수 있다.

### P3 — 품질과 접근성

- 관리자 웹의 작은 영문 eyebrow와 보조 텍스트는 대비와 크기가 낮다.
- 표의 점 세 개, 아이콘 전용 버튼에는 보이는 이름 또는 일관된 툴팁이 필요하다.
- QR 화면의 접근성 트리에는 원시 `Choose File` 컨트롤이 노출된다. 사용자 언어와 보이는 버튼 이름을 맞춰야 한다.
- 카드 목록·상세의 깨진 이미지에서는 alt 텍스트가 레이아웃을 밀어낸다. 에러 fallback이 동일 크기를 유지해야 한다.
- 애니메이션 카드 공개, 자동 스크롤, 온보딩 전환은 `prefers-reduced-motion`에서도 핵심 정보를 잃지 않아야 한다.
- 폼 오류는 색상·토스트만이 아니라 해당 필드와 연결된 텍스트로 제공해야 한다.

## 세 앱을 하나의 제품으로 만드는 추가 기능

### 1. 통합 릴리스 워크스페이스

카드마다 다음 상태를 한 타임라인에서 공유한다.

`아티스트 초안 → 미디어 준비 → 검수 요청 → 운영 코멘트 → 승인/수정 요청 → 공개 일정 → 드롭/코드/상품 연결 → 팬 공개 → 수집·반응 분석`

스튜디오와 관리자 모두 같은 체크리스트·버전·담당자·마감·코멘트를 보되 역할에 맞는 편집 권한만 다르게 해야 한다. 팬앱에 실제 노출된 URL과 썸네일도 릴리스 기록에 남겨야 한다.

### 2. 관리자 전역 준비도와 영향 미리보기

공개 버튼을 누르기 전에 다음을 한 번에 검사한다.

- 필수 미디어와 접근 가능한 이미지 URL
- 카드·팩·드롭·코드·상품·이벤트·보상의 참조 무결성
- 팬앱 홈·탐색·아티스트 홈에서 보일 위치
- 대상 팬 수와 알림 수신 예상치
- 공개 취소·수정 시 영향을 받는 주문·소유권·이벤트

### 3. 아티스트 공개 카드 카탈로그

개인 보관함과 독립된 아티스트별 공개 카드 화면을 만든다. 모든 공개 카드, 시즌, 카드팩, 희귀도, 소유 여부, 원하는 카드, 거래 가능 여부를 한곳에서 볼 수 있어야 한다.

### 4. 거래 의도 모델 재설계

`관심`, `원함`, `내놓음`을 분리하고, 양쪽 의도가 맞으면 교환 후보를 추천한다. 추천 이유, 예상 가치 범위, 카드 잠금 상태, 제안 만료와 취소 조건을 명확히 보여준다.

### 5. 설명 가능한 팬 추천

규칙 기반 점수부터 시작하고 추천 이유를 저장한다. 관리자는 가중치와 안전 필터를 보고 조정할 수 있어야 하며, 팬은 추천 숨기기·관심 없음·차단으로 피드백할 수 있어야 한다.

### 6. 오프라인 사전녹화·팬 이벤트 운영 모드

현재 이벤트와 QR 기반을 확장해 신청 방식 선택, 최소 자격 자동 확인, 참석 시간 슬롯, 현장 체크인 QR, 신원 확인 결과만 저장하는 검증, 순번·대기 상태, 번호표·특전 포토카드 지급을 연결한다. 선착순·추첨·조건 충족 후 추첨을 파트너가 선택할 수 있어야 한다.

현장에서는 모든 참가자가 줄을 설 필요 없이 여러 체크인 포인트에서 QR을 처리하되, 대리 인증을 막기 위해 인증 완료 후 짧은 유효시간의 동적 체크인 토큰과 직원의 최종 육안 확인을 결합하는 것이 현실적이다. 외국인은 PASS만 강제하지 말고 여권·외국인 신분증 등 파트너 정책에 따른 별도 검증 경로를 둔다.

### 7. 아티스트용 팬 반응 분석

수집 수 외에 노출 → 상세 보기 → 저장 → 등록/구매 → 미디어 재생 → 완료 → 공유를 보여준다. 개인 식별 정보 없이 카드 버전별 반응, 이탈 지점, 팬 코멘트 주제를 비교할 수 있어야 다음 제작에 도움이 된다.

### 8. 알림 인박스의 실제 작업 연결

알림을 누르면 정확한 카드 검수 버전, 고객 문의, 이벤트 신청, 거래 제안으로 이동해야 한다. 사용자별 즉시·일간 요약, 채널별 수신, 조용한 시간 설정도 필요하다.

### 9. 소유권·발급 이력 뷰

팬은 카드 상세에서 발급 원천, 최초 취득 시각, 소유권 변경, 거래 잠금, 취소·회수 여부를 이해할 수 있어야 한다. 관리자는 같은 기록의 감사 로그와 원장 해시/서명을 확인해야 한다. NFT 없이도 변경 불가능한 소유권 원장과 백업·복구 검증을 제품 기능으로 드러낼 수 있다.

### 10. 성능 예산과 라우트 단위 로딩

이번 팬앱 빌드는 CSS 약 468 kB, 주요 JavaScript 청크가 약 478 kB와 545 kB로 생성됐고 500 kB 초과 경고가 있었다. 라우트 단위 코드 분할, QR·Firebase 등 비핵심 라이브러리 지연 로딩, 화면별 CSS 분리, 이미지 변환·responsive source·캐시 정책을 릴리스 기준으로 만든다.

또한 개발 서버에서는 팬앱 루트가 빈 화면으로 남고 같은 소스의 프로덕션 빌드 미리보기만 정상 동작했다. 프로덕션 UX와 별개로, 로컬 피드백 루프와 E2E 신뢰도를 떨어뜨리는 개발 환경 결함이므로 별도 수정이 필요하다.

## 감사 증거와 제한

### 실제로 검증한 연결

- 아티스트 스튜디오에서 카드 초안 생성 및 재조회
- 누락 음성 파일로 검수 요청 차단
- 생성한 초안이 관리자 카드 목록에 반영됨
- 팬 코드 등록으로 사용자 카드 소유권과 감사 활동 생성
- 비동기 성장 이벤트가 `processed`가 되고 XP 원장 30 및 팬 레벨 30이 DB에 기록됨
- 팬 화면에는 같은 시점 이후에도 0 XP가 남는 상태 재현

### 이번 감사에서 제한된 부분

- 격리 시드에 실제 이벤트가 없어 팬 신청 상세, 관리자 참석자 운영, 현장 체크인까지는 실행하지 못했다.
- 다른 팬의 온보딩·거래 가능 카드 조건이 준비되지 않아 실제 양방향 거래 제안·수락까지는 실행하지 않았다.
- 외부 이메일, 푸시, 결제 사업자, 실제 파일 스토리지 전송은 로컬 감사 범위 밖이다.
- 팬앱의 개발 서버 빈 화면 때문에 팬 여정은 같은 소스의 성공한 프로덕션 빌드 미리보기에서 검증했다.

## 후속 구현 상태

- 이벤트 현장 체크인은 개인정보를 QR에 넣지 않는 서명 패스로 구현했다. 팬 신청자는 패스를 발급받고, 운영자는 관리자 이벤트 화면에서 검증하며, 서버는 패스 해시와 체크인 시각을 보관한다.
- 패스는 이벤트 범위와 신청 건에 묶이고 행사 시간 밖에서는 거부되며, 동일 패스를 다시 스캔하면 이미 체크인된 결과를 반환해 중복 입장을 막는다.
- 관리자 신청자 목록에는 체크인 상태가 표시되고, 카메라 연동이 없는 운영 단말을 위해 패스 값 입력 검증도 제공한다.
- 이벤트 배너는 업로드 완료 시점에 팬앱용 1200×600 WebP 파생본을 미리 생성해 첫 홈 조회에서 원본 변환을 기다리지 않도록 보완했다. 기존 자산은 공개 조회 시 호환 fallback으로 지연 생성될 수 있다.
- 팬앱 초기 진입 번들은 카드 상세, 설정, QR 등록 모달을 React lazy/Suspense 경계로 분리했다. 공용 QR 아이콘을 별도 모듈로 추출해 QR 모달도 실제 청크로 분리했고, 관련 CSS도 별도 청크로 생성된다. 재빌드 기준 초기 JS는 479.26 kB로 확인되어 이전 512.25 kB보다 줄었지만, 의존성 청크 `esm-VHHMf48Z.js`는 여전히 477.54 kB이므로 전체 성능 예산을 닫으려면 의존성 분석과 추가 분할이 필요하다.
- 네이티브 QR 카메라 스캔 및 외국인 신원 문서/얼굴 대조는 개인정보·법무·기기별 정책 결정이 필요한 별도 범위로 남겼다. 현재 구현은 운영자 확인을 대체한다고 주장하지 않는다.
