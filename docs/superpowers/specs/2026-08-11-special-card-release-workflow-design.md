# 스페셜 카드 제작·검수·발행 연동 설계

## 목적

아티스트가 Artist Studio에서 스페셜 카드를 제작하고, 담당 회사와 Fanfolio 플랫폼 운영자가 역할에 따라 검수하며, 승인된 카드만 드롭·QR/코드 발급을 거쳐 팬앱에 공개하는 단일 운영 흐름을 만든다.

현재의 세 앱은 같은 카드 데이터를 일부 공유하지만, 검수 책임·알림·발행 준비의 상태 전환이 분리돼 있다. 이 설계는 모든 앱이 같은 카드 릴리스 상태와 검수 스냅샷을 사용하도록 한다.

## 역할과 책임

| 역할 | 제작 | 회사 콘텐츠 승인 | 플랫폼 공개 승인 | 드롭·코드 작업 | 정책·예외 |
| --- | --- | --- | --- | --- | --- |
| 아티스트 스튜디오 계정 | 가능 | 불가 | 불가 | 불가 | 불가 |
| 회사 관리자 / 매니저 | 불가 | 가능 | 불가 | 승인 뒤 가능 | 불가 |
| 플랫폼 운영 관리자 | 불가 | 불가 | 가능 | 최종 공개 가능 | 불가 |
| 루트 관리자 | 불가 | 불가 | 불가 | 불가 | 가능 |

플랫폼 운영 관리자는 루트와 별도인 내부 운영 역할이다. 여러 명을 등록할 수 있고, 필요한 경우 그중 한 명의 승인으로 플랫폼 검수 조건을 충족한다. 루트 관리자는 개별 카드 공개에 관여하지 않으며 회사 검수 정책의 상향·예외와 감사에만 접근한다.

## 검수 정책

정책은 회사별 기본값을 사용하고 카드별 예외는 상향만 허용한다.

- 일반 카드: 회사 관리자 또는 매니저 1명 승인
- Special 카드: 회사 승인 1명과 플랫폼 운영 관리자 승인 1명
- 카드별 예외: 회사 관리자가 근거를 남겨 플랫폼 검수를 추가할 수 있다.
- 정책 완화: 루트 관리자만 수행할 수 있고 감사 로그에 남긴다.

회사는 스스로 공개 장벽을 낮출 수 없다. Special 카드는 기본적으로 플랫폼 검수를 우회할 수 없다.

## 카드 릴리스 상태

```text
draft
  → pending_partner_review
  → changes_requested ──→ draft (새 검수 버전)
  → pending_platform_review (Special 또는 상향 카드만)
  → approved
  → drop_ready
  → published
```

`approved`는 모든 필수 검수 승인이 충족된 상태다. `drop_ready`는 카드가 하나 이상의 드롭에 연결돼 QR/코드 발행 준비가 된 상태이며, 팬앱 노출은 드롭이 라이브이면서 카드가 `published`일 때만 가능하다.

## 검수 스냅샷과 수정

검수 요청 시 카드의 이미지, 앞·뒷면 디자인 구성, 보이스·영상 자산, 홀로그램 설정, 카드 메타데이터 및 아티스트 메모를 하나의 검수 버전으로 저장한다.

검수 대기 중 아티스트가 편집하면 기존 요청을 바꾸지 않는다. 새 초안 버전을 만들며, 다시 제출하면 이전 요청은 대체됨으로 기록된다. 반려 또는 수정 요청에는 사유와 요청자·시각을 남기고 스튜디오 작업 화면에 그대로 표시한다.

## 알림

알림은 수신자별 읽음 상태를 가지며 같은 상태 전환에 대해 한 번만 생성한다.

| 이벤트 | 수신자 | 내용 |
| --- | --- | --- |
| 검수 요청 | 해당 카드 아티스트 범위를 맡은 회사 관리자·매니저 | 검수 대기 카드, 제출자, 기한 |
| 회사 승인 완료 | 아티스트, 플랫폼 운영 관리자(필요 시) | 다음 검수 단계 또는 발행 준비 안내 |
| 수정 요청 | 아티스트 | 수정 사유와 검수 버전 |
| 플랫폼 검수 요청 | 플랫폼 운영 관리자 | Special/상향 카드 대기 알림 |
| 최종 승인 | 회사 담당자, 아티스트 | 드롭·코드 발급 가능 안내 |
| 공개 완료 | 아티스트, 회사 담당자 | 팬앱 공개와 드롭 상태 |

알림은 관리자 상단 벨과 작업 대기열에서 확인하며, 이메일·외부 알림은 이후 별도 전달 채널에서 확장한다.

## 드롭·QR/코드·팬앱 연동

1. 회사 관리자 또는 매니저는 `approved` 카드만 자기 회사·배정 아티스트 범위의 드롭에 연결한다.
2. 드롭은 공개 수량, 기간, 대상 카드, QR/코드 배치를 가진다.
3. 라이브 전환 후 팬이 QR/코드를 등록하면 기존 컬렉션 API가 소유권을 기록한다.
4. 팬앱 탐색과 카드 상세는 공개 카드만 조회하며 스튜디오의 미디어 구성(보이스, 영상, 손글씨, 홀로그램)을 카드 상세에 렌더링한다.

드롭 또는 코드 생성 실패는 카드 상태를 되돌리지 않는다. 발행 준비 화면에 실패 원인과 재시도 동작을 제공한다.

## 관리자 UX 범위

- 회사 관리자에게만 의미 없는 “내 회사 운영 범위”, “루트 관리자 관리 범위” 상태 라벨은 제거한다.
- 데스크톱 좌측 내비게이션은 접기/펼치기할 수 있고, 펼친 상태의 하단 계정 영역에서 로그아웃을 항상 제공한다.
- 상단 아바타는 계정 메뉴를 열며 계정 설정, 비밀번호 변경, 로그아웃을 제공한다.
- 스튜디오 검수 요청은 관리자 상단 알림 벨과 카드 검수 대기열에 같은 수로 표시한다.
- 카드 검수 상세는 스튜디오에서 제출한 스냅샷, 미디어 체크, 검수 이력, 승인 조건, 다음 가능한 동작을 한 화면에 표시한다.

## API 및 데이터 경계

- 카드: `releasePolicy`, `releaseStatus`, `reviewVersion`, `reviewSnapshot`, `partnerApproval`, `platformApproval`, `platformReviewRequired`를 가진다.
- 검수 요청: 카드 버전별 승인·반려·수정 요청 기록을 가진다.
- 알림: 수신자, 이벤트 키, 관련 카드/드롭 ID, 읽음 시각을 가진다.
- 드롭 생성 API는 `approved` 상태와 조직·아티스트 권한을 서버에서 검증한다.
- 모든 검수, 정책 예외, 공개, 코드 배치 생성은 감사 로그에 조직·아티스트·카드·행위자를 남긴다.

## 오류 처리와 보안

- API는 UI 숨김과 무관하게 역할·조직·아티스트 범위를 검증한다.
- 불완전한 보이스·영상·카드 이미지가 활성화된 상태면 검수 요청을 거부한다.
- 승인 조건이 충족되기 전에는 드롭 연결 및 공개 API를 거부한다.
- 비밀번호 재발급이나 역할 변경은 기존 세션을 폐기하며, 임시 비밀번호는 한 번만 응답·표시한다.

## 검증 기준

- 스튜디오 제출이 회사 담당자의 관리자 알림/검수 대기열에 표시된다.
- 일반 카드와 Special 카드가 서로 다른 승인 조건을 강제한다.
- 회사·플랫폼 승인 중 하나가 빠지면 `approved`로 전환되지 않는다.
- 승인된 카드만 드롭·코드 생성이 가능하다.
- 라이브 드롭의 공개 카드만 팬앱 탐색·상세에 노출된다.
- 회사 관리자, 매니저, 플랫폼 운영 관리자, 루트 관리자의 API 권한 거부 사례를 계약 테스트로 고정한다.
