# 팬앱 관심·좋아요 기능 설계

## 목표

팬앱에서 보이는 관심/하트 조작이 새로고침과 화면 재진입 뒤에도 유지되고, 팔로우 추천과 실제 사용자 행동 데이터가 서로 혼동되지 않도록 한다.

## 범위

- 아티스트 관심은 기존 사용자 프로필의 `favoriteArtistIds` 저장 계약을 사용한다.
- 카드 관심은 기존 `fan_wishlist_items`와 `/me/wishlist` 계약을 홈·카드 상세에서 공통 사용한다.
- 이벤트 좋아요는 이벤트별 사용자 관계를 저장하는 별도 `event_likes` 모델과 API를 추가한다.
- 모든 서버 저장 조작은 인증된 팬만 가능하며, 중복 추가/반복 삭제는 멱등적으로 처리한다.
- 미리보기 데이터(`initialItems`)에서는 서버 저장을 시도하지 않으며, 저장 기능처럼 보이는 낙관적 토글을 허용하지 않는다.

## 데이터 흐름

1. 화면 진입 시 사용자 프로필, 위시리스트, 이벤트 좋아요 목록을 API로 조회한다.
2. 하트의 초기 상태는 조회 결과로 계산한다.
3. 사용자가 토글하면 서버 mutation을 먼저 호출하고 성공 응답으로 상태를 확정한다.
4. 실패하면 기존 상태를 유지하고 접근 가능한 오류 메시지를 표시한다.

## 이벤트 좋아요 API

- `GET /api/me/event-likes` — 현재 사용자의 좋아요 이벤트 ID 목록
- `PUT /api/me/event-likes/{event_id}` — 좋아요 추가, 이미 있으면 동일한 성공 응답
- `DELETE /api/me/event-likes/{event_id}` — 좋아요 삭제, 없어도 동일한 성공 응답
- 존재하지 않거나 공개되지 않은 이벤트에는 좋아요를 추가할 수 없다.

## UI 계약

- 홈 이벤트 배너 하트는 이벤트 좋아요 API에 연결한다.
- 홈 아티스트 하트는 기존 프로필 저장 흐름을 호출하고 저장 중 상태를 표시한다.
- 홈 새 카드 하트는 위시리스트 API를 호출한다.
- 카드 상세의 하트는 기존 위시리스트 API를 유지하되, 컬렉션 카드 상세의 독립적인 로컬 `useState` 토글은 제거하거나 위시리스트 상태로 연결한다.
- API가 없는 미리보기 화면에서는 하트를 숨기거나 비활성화해 가짜 저장 성공을 만들지 않는다.

## 오류·보안

- 모든 mutation은 팬 인증과 대상 리소스 공개 상태를 확인한다.
- 이벤트 좋아요에는 사용자-이벤트 유니크 제약을 둔다.
- 차단·삭제된 사용자나 비공개 이벤트는 조회·변경 대상에서 제외한다.
- 실패 응답은 UI에 표시하되 내부 오류 상세나 인증 정보를 노출하지 않는다.

## 검증

- 백엔드 계약 테스트: 이벤트 좋아요 등록/재등록/삭제/재삭제/비공개 차단.
- 기존 테스트: 팔로우 추천·위시리스트·프로필 저장 회귀.
- 프론트엔드 테스트: 홈 이벤트/아티스트/카드 하트의 API 호출, 성공 상태 유지, 실패 롤백.
- lint, typecheck/build, 관련 전체 테스트를 실행한다.
