## 문서 요약

### 한 문장 정의

Fanfolio는 아티스트와 파트너사가 직접 만든 디지털 포토카드를 카드팩·이벤트·팬 패스·인증번호로 발급하고, 팬이 이를 수집·전시·조합·거래하는 팬 컬렉션 서비스다.

### 핵심 사용자 경험

`발견 → 획득 → 컬렉션 저장 → 카드 상세 감상 → 중복 활용 → 다른 팬과 공유·거래`

팬은 카드팩을 열거나 이벤트·팬 패스·QR·인증번호를 통해 카드를 얻는다. 획득한 카드는 서버에 소유권이 기록되고 컬렉션에 표시된다. 팬은 카드의 앞면·뒷면·아티스트 메시지·음성·영상·효과·획득 기록을 확인하며, 이후 중복 카드 조합이나 제한적 거래를 통해 컬렉션을 확장한다.

### 운영 구조

| 주체 | 핵심 책임 |
| --- | --- |
| 루트 관리자 | 전체 시스템·권한·파트너·감사 정책 |
| 일반 관리자 | 팬 패스·이벤트·미션·업적·전체 발급 운영 |
| 파트너 매니저 | 자기 파트너의 아티스트·카드·카드팩·구성원 관리 |
| 하위 관리자 | 상품기획·아티스트 운영 등 부여된 범위의 업무 |
| 아티스트 스튜디오 사용자 | 카드 콘텐츠 제작·저장·검수 요청 |
| 팬 | 카드 획득·수집·전시·조합·거래·팔로잉 |

### 제품의 핵심 원칙

1. 카드의 모든 소유권과 발급 이력은 서버 원장에서 관리한다.
2. 확률·발급 수량·획득 경로는 팬에게 투명하게 공개한다.
3. 공개된 카드팩과 카드 구성은 버전으로 고정하고 변경 시 새 버전을 만든다.
4. 아티스트와 하위 관리자는 콘텐츠를 만들 수 있지만 승인·공개·발급 권한은 분리한다.
5. 거래·조합·인증번호 등록은 중복 처리와 경쟁 조건을 서버에서 차단한다.
6. 팬의 컬렉션 공개 범위와 차단·신고 권한을 보장한다.

| 팔로잉·컬렉션 공개 | 구현·안전성 보강 | 팔로우 상태·공개 컬렉션·차단 시 검색/컬렉션/팔로우 제한 계약 테스트 |

현재 배포 판단은 `카드 상세 UI 수정 검증 완료`와 `전체 서비스 배포 승인`을 구분한다. 전체 서비스 배포는 아래 핵심 시나리오가 실제 로컬 백엔드에서 완주된 뒤에만 승인한다.

### 현재 실행 기준 기록

- `test_artist_card_reaches_fan_collection_after_review_and_pack_release` 최초 실행에서 카드팩 공개 시 `PACK_CARDS_NOT_PUBLISHED`가 확인되었다.
- 검수 승인(`approved`)과 카드 공개(`published`)는 별도 상태 전이이므로, 기준 시나리오에 루트 관리자 카드 공개 단계를 명시한다.
- 카드팩 공개 전 카드 공개가 누락되면 테스트가 중단되어야 하며, 팬 컬렉션에는 발급 카드가 생성되지 않아야 한다.
- `test_card_ownership_ledger.py`에서 동일 `Idempotency-Key`의 카드팩 개봉이 `UserCard`와 원장 행을 각각 한 건만 생성하는지 확인한다.
- `test_card_ownership_service.py`에서 공통 카드 발급 서비스가 동일 소유권 이벤트를 한 번만 반영하고, 미공개 카드 실패 시 `UserCard`·원장 행을 만들지 않는지 확인한다.
- 인증번호 등록도 `redeem_code` 원장 이벤트를 하나만 남기는지 확인한다.
- `test_card_role_scope_matrix.py`에서 아티스트의 공개 API 차단과 파트너 간 카드 범위 격리를 확인한다.
- 백엔드 계약 테스트 전체 실행 결과: `258 passed` (기존 Starlette/httpx deprecation warning 1건).
- 팬 앱 계약 테스트 결과: `133 passed`; 관리자 카드 운영 관련 계약 테스트 결과: `46 passed`.
- 기준 출시 시나리오 `test_artist_card_reaches_fan_collection_after_review_and_pack_release`는 고정 역할 fixture(root/general admin, partner manager/editor, artist studio, fan)로 카드 제출 → 파트너 검수 승인 → 루트 공개 → 카드팩 공개 → 팬 개봉 → 컬렉션 반영을 통과했다.
- 프론트 `product-scenario-contract.test.mjs`는 실 API 경로, 공개/개봉/공개 카드 추가 완료 이동, 컬렉션 새로고침 계약을 포함해 전체 133개 테스트로 통과했다.
- 현재 확인된 범위는 백엔드·계약 테스트와 격리 DB 기반 팬앱·관리자 브라우저 E2E다. 관리자 카드팩 생성·공개 API, 관리자 카드팩 조회, 팬앱 카드팩 확률표·개봉·컬렉션·상세, 인증코드 성공·중복·미공개 코드 차단까지 확인했다.
- 로컬 SQLite에는 `0043_card_ownership_ledger`를 적용했고 Alembic head 상태를 확인했다.
- 로컬 백엔드 `8002`의 읽기 전용 `GET /api/catalog/card-packs`는 `200`을 반환했다. 테스트 DB 전체 초기화는 기존 로컬 데이터 보존을 위해 실행하지 않았다.
- 기존 로컬 DB를 보존하기 위해 `/private/tmp/fanfolio-e2e.db` 복사본이 아닌 별도 테스트 DB를 사용해 브라우저 검증을 실행했다. 팬앱 개발 서버는 임시 백엔드 `8003`에 연결했다.
- Codex 내장 브라우저 팬앱 E2E: 임시 팬 계정 생성·온보딩 → 인증코드 `NOVA-VALID-01` 입력 → 카드 확인 → 카드 공개 → 컬렉션 추가 → 보관함 표시 → 카드 상세 독립 화면 → 뒷면 전환까지 완료했다.
- 팬앱 화면에서 컬렉션 진행률이 `0 / 9`에서 `1 / 9`로 변경되고, 카드 상세에 등급·카드 번호·획득일·아티스트 메시지와 앞면/뒷면 인터랙션이 표시되는 것을 확인했다.
- Codex 내장 브라우저 관리자 웹 프리뷰에서 카드 관리·카드팩 관리·카드 구성 편집·발급·인증번호 화면과 공개 확률 100%, 카드 구성 7장, 발급 배치 상세 및 CSV 내보내기 버튼을 확인했다. 단, 현재 `admin_app`은 정적 프리뷰이므로 이 브라우저 확인은 관리자 API mutation 검증이 아니라 화면 계약 확인이다.
- Codex 내장 브라우저 관리자 웹을 임시 백엔드 `8003`에 연결해 로그인·대시보드·카드 목록·카드팩 목록을 실제 API로 조회했다. 관리자 API로 테스트 카드팩을 생성·공개한 뒤 대시보드의 공개 카드팩과 최근 활동(`card_pack.created`, `card_pack.published`)에 반영되는 것을 확인했다.
- 팬앱 `/collection/cards`에서 공개 카드팩과 `100%` 확률표가 표시되고, `팩 열기` 실행 후 서버에 개봉 기록이 생성되며 새로고침 뒤 `0 / 1`에서 `1 / 1`로 컬렉션에 반영되었다. 카드 상세 독립 화면에서 아티스트 메시지·획득 경로·발행 수량을 확인했다.
- 팬앱 인증번호 등록에서 유효 코드 등록은 완료되었고, 같은 코드를 다시 등록하면 `사용할 수 없는 코드입니다.`, 미공개 코드는 `공개되지 않은 카드입니다.`로 차단되었다. 이후 관리자가 신규 1회용 발급 배치를 생성하고 QR PNG를 발급한 뒤, 사용자가 실제 QR을 스캔해 카드 확인 → 카드 공개 → 컬렉션 추가까지 완료했다. 등록 완료 화면에서 컬렉션 진행률 `1 / 9`, 카드 등급·시즌·획득 보상이 표시되는 것을 확인했다.
- 관리자 카드 등록 UI는 이미지 파일 업로드가 필수이며 현재 Codex 브라우저 커넥터가 파일 첨부 API를 제공하지 않아 등록→검수→공개 UI 연속 검증은 보류했다. presign/upload API 계약과 상태 전이는 검증했으며, 실제 파일 첨부가 가능한 브라우저 세션에서 최종 게이트를 수행한다.

### MVP와 후속 범위

#### MVP — 배포 전 반드시 검증할 범위

- 관리자·파트너·스튜디오 사용자 권한 분리
- 카드 등록 → 검수 요청 → 승인 → 공개
- 카드팩 생성 → 카드 구성 → 확률 검증 → 공개
- 팬 앱의 카드팩·확률표 노출
- 카드팩 개봉 결과의 팬 컬렉션 반영
- 특별 카드 발급 배치와 고유 인증번호
- QR·인증번호 등록 성공·중복·오류 처리
- 카드 상세 독립 화면과 새로고침·뒤로가기
- 소유권·감사 로그·기본 운영 통계

#### 2단계 — 핵심 서비스 확장

- 중복 카드 조합
- 제한적 카드 트레이딩
- 팔로잉·컬렉션 공개·차단
- 알림 센터
- 카드 검색·위시리스트·수집 목표
- 신고·콘텐츠 안전

#### 3단계 — 차별화 기능

- 컬렉션 전시 공간
- 아티스트 활동 연동 카드
- 아티스트 스튜디오 효과 프리셋
- 고급 레이어·타임라인·입자 효과 편집

### 이 문서를 읽는 순서

1. 이 요약에서 제품 범위와 현재 상태를 확인한다.
2. `6. 핵심 검증 시나리오`에서 실제 사용자·운영자 흐름을 확인한다.
3. `7. 배포 승인 게이트`와 `18. 추가 배포 승인 게이트`를 배포 전 체크리스트로 사용한다.
4. 카드 조합·거래·소셜·스튜디오 세부 규칙은 해당 상세 절을 참고한다.

## 1. 제품 운영 모델

Fanfolio는 팬 앱과 운영자 웹을 하나의 카드 발급 서비스로 연결한다.

- 루트 관리자: Fanfolio 서비스를 만든 운영 주체. 전체 시스템, 권한 정책, 파트너 승인, 감사 및 운영 기준을 관리한다.
- 일반 관리자: Fanfolio 백오피스 운영자. 전체 팬 패스, 파트너, 이벤트, 미션, 업적, 카드 발급 운영을 관리한다.
- 파트너사 매니저: 계약된 파트너사의 대표 관리자. 자기 파트너 범위의 아티스트, 팀, 카드, 카드팩, 이벤트와 구성원을 관리한다.
- 파트너사 하위 관리자: 매니저가 초대한 운영 계정. 상품기획, 아티스트 운영, 콘텐츠 제작 등 팀별로 허용된 기능만 사용한다.
- 아티스트 스튜디오 사용자: 파트너사가 권한을 부여한 아티스트 또는 제작자. 카드 콘텐츠를 만들고 검수를 요청하지만, 승인·공개·발급 권한은 기본적으로 갖지 않는다.
- 팬: 카드팩, 이벤트, 팬 패스, QR, 인증번호 등 허용된 경로를 통해 카드를 획득하고 팬 컬렉션에서 확인한다.

## 2. 권한 원칙

권한은 계정 유형이 아니라 `파트너 범위 + 아티스트 범위 + 기능 권한`의 조합으로 판정한다.

| 기능 | 루트 관리자 | 일반 관리자 | 파트너 매니저 | 하위 관리자 | 스튜디오 사용자 | 팬 |
| --- | --- | --- | --- | --- | --- | --- |
| 전체 운영 정책·권한 관리 | 가능 | 제한 | 불가 | 불가 | 불가 | 불가 |
| 파트너 등록·계약 범위 관리 | 가능 | 가능 | 자기 파트너만 | 불가 | 불가 | 불가 |
| 팬 패스·전체 레벨 관리 | 가능 | 가능 | 협의/제한 | 불가 | 불가 | 조회/참여 |
| 이벤트·미션·업적 관리 | 가능 | 가능 | 자기 파트너만 | 권한 부여 시 | 불가 | 참여 |
| 기본 카드 등록 | 가능 | 가능 | 가능 | 권한 부여 시 | 스튜디오에서 생성 |
| 카드팩·버전·확률 관리 | 가능 | 가능 | 가능 | 권한 부여 시 | 불가 |
| 카드 검수 요청 | 가능 | 가능 | 가능 | 가능 | 가능 |
| 카드 승인·공개·발급 | 가능 | 가능 | 정책에 따라 요청 | 불가 또는 승인 요청 | 불가 | 불가 |
| 구성원 초대·권한 부여 | 가능 | 정책에 따라 가능 | 자기 파트너 하위만 | 불가 | 불가 | 불가 |
| 인증번호·발급 배치 관리 | 가능 | 가능 | 자기 파트너만 | 권한 부여 시 | 불가 | 코드 사용 |

권한 검증은 화면에 버튼을 숨기는 것만으로 끝내지 않는다. 모든 생성·수정·검수·공개·발급 API에서 서버가 최종 권한을 재검사해야 한다.

## 3. 카드 생명주기

카드는 다음 상태를 거친다.

`작성 중 → 검수 요청 → 검수 중 → 승인됨 → 공개됨 → 발급 가능 → 팬 보유 → 회수/중지(필요 시)`

### 3.1 기본 카드

파트너사 운영자 또는 권한을 받은 관리자가 앨범, 시즌, 카드팩에 포함할 포토카드를 등록한다.

필수 데이터:

- 아티스트, 앨범/시즌, 카드팩 버전
- 카드 번호, 멤버, 희귀도
- 앞면 이미지, 뒷면 이미지
- 카드 설명, 아티스트 메시지
- 발행 방식: 카드팩 랜덤, 한정 특전, 이벤트, 팬 패스 등
- 카드 타입과 공개 상태

### 3.2 아티스트 스튜디오 카드

아티스트 또는 제작자는 모바일·태블릿·컴퓨터에서 스튜디오에 접속해 다음 콘텐츠를 만들 수 있다.

- 음성 메시지
- 모션 또는 영상
- 손글씨, 사인, 그림
- 비공개 이스터에그
- 특정 이벤트에서만 활성화되는 효과

스튜디오 사용자는 카드의 초안을 저장하고 검수를 요청한다. 승인 전 카드는 팬에게 노출되거나 발급될 수 없다.

### 3.3 특별 카드

특별 카드는 카드팩에 포함되지 않고 특정 이벤트·특전·팬 패스·인증번호를 통해 발급될 수 있다. 제한 수량 카드라면 발급 배치 생성 시 수량만큼 고유 인증번호를 미리 생성하고, 무제한 랜덤 카드라면 발급 순간 고유 식별자를 생성한다.

모든 인증번호는 전역 유일해야 하며 다음을 보장해야 한다.

- 중복 생성 방지: 데이터베이스 유니크 제약 + 서버 재시도 안전성
- 원문 인증번호 비노출 저장 또는 안전한 해시 저장
- 사용 전·사용 완료·취소·만료 상태 관리
- 동일 팬의 중복 등록 방지
- 사용 이력, 발급 배치, 카드, 사용자, 시각 감사 로그 기록

## 4. 카드팩 및 확률 운영

한 시즌 또는 앨범에 여러 카드팩을 둘 수 있다. 예를 들어 `정규 1집 · DREAMSCAPE` 아래에 `Nebula Ver.`, `Starlight Ver.`, `Midnight Ver.`를 둘 수 있다.

카드팩은 다음 정보를 가진다.

- 카드팩 이름, 버전, 대표 이미지, 설명
- 소속 아티스트와 시즌/앨범
- 포함 카드 목록
- 카드별 희귀도와 확률
- 확률 합계 검증 결과
- 공개 상태와 버전
- 공개된 확률표의 변경 이력

확률은 팬 앱에서 항상 공개한다. 공개된 버전은 직접 수정하지 않고 새 버전을 만들어 검수·공개한다. 새 버전은 먼저 기본 정보를 등록한 뒤 카드 구성과 확률을 편집하고, 검수 승인 후 서비스에 노출한다.

확률 검증 규칙:

- 모든 포함 카드의 확률은 0보다 크고 유효한 숫자여야 한다.
- 카드별 확률 합계는 정확히 100%여야 한다.
- 등급별 요약과 카드별 상세 합계가 일치해야 한다.
- 공개 시점의 확률표를 발급 결과와 함께 보존해야 한다.
- 재고가 제한된 경우 실제 잔여 수량과 확률 정책을 별도로 표시해야 한다.

## 5. 팬 획득 및 컬렉션 흐름

팬은 다음 경로 중 하나로 카드를 획득한다.

1. 카드팩을 열고 공개 확률에 따라 카드가 발급된다.
2. 이벤트 참여 조건을 충족하고 특별 카드 또는 인증번호를 받는다.
3. 파트너사가 제공한 QR을 스캔하거나 인증번호를 입력한다.
4. 팬 패스 또는 전체 레벨 보상으로 카드를 받는다.
5. 특정 업적·미션·이스터에그 조건을 충족해 카드를 받는다.

공통 성공 조건:

- 발급 또는 코드 사용이 성공하면 팬의 보유 카드가 서버에 저장된다.
- 팬 컬렉션에 카드가 즉시 또는 새로고침 후 표시된다.
- 카드 상세에서 앞면·뒷면·카드 정보·아티스트 메시지·효과·획득 경로를 확인할 수 있다.
- 카드 상세는 독립 경로(`/cards/:id`)로 열리며 컬렉션 위에 모달로 덧씌워지지 않는다.
- 카드 뒷면에서도 틸트 상호작용이 동작한다. 단, 뒷면에는 불필요한 광원 효과를 적용하지 않는다.
- 동일 카드를 여러 장 보유하면 보유 수량이 증가하고 컬렉션 슬롯은 중복 상태를 표시한다.

## 6. 핵심 검증 시나리오

### 시나리오 A — 파트너사가 기본 카드팩을 만들어 팬에게 공개

1. 루트 관리자가 파트너사를 등록하고 파트너 매니저 계정을 발급한다.
2. 파트너 매니저가 하위 관리자를 초대하고 상품기획팀·아티스트팀 권한을 부여한다.
3. 하위 관리자가 아티스트, 앨범/시즌, 카드팩 기본 정보를 등록한다.
4. 승인된 카드 목록에서 카드를 카드팩에 추가한다.
5. 카드별 확률을 입력하고 합계 100% 검증을 통과한다.
6. 검수 요청 후 일반 관리자 또는 승인 권한자가 승인한다.
7. 팬 앱에서 해당 아티스트를 관심 등록한 팬에게 카드팩이 노출된다.
8. 팬 앱에서 확률표를 확인하고 카드팩을 연다.
9. 발급된 카드가 팬 컬렉션에 저장된다.
10. 컬렉션에서 해당 카드를 눌러 독립 카드 상세 화면을 열고 앞면·뒷면·메시지·효과·메타데이터를 확인한다.

판정: 모든 단계가 같은 백엔드 데이터로 연결되고, 새로고침 후에도 결과가 유지되어야 통과한다.

### 시나리오 B — 아티스트가 특별 카드를 만들고 검수 후 한정 발급

1. 파트너 매니저가 아티스트 스튜디오 접근 권한을 부여한다.
2. 아티스트가 카드 앞면·뒷면·메시지·음성/모션/손글씨/사인 중 하나 이상을 제작한다.
3. 아티스트가 초안을 저장하고 검수를 요청한다.
4. 관리자가 카드 상세와 미디어를 확인하고 승인 또는 반려한다.
5. 승인된 카드에 발급 방식, 제한 수량, 이벤트/특전 조건을 설정한다.
6. 관리자가 발급 배치를 만들고 제한 수량만큼 고유 인증번호를 생성한다.
7. CSV 내보내기 또는 운영자용 조회로 배치 수량과 인증번호 상태를 확인한다.
8. 팬이 QR 또는 인증번호로 카드를 등록한다.
9. 이미 사용한 코드, 다른 카드의 코드, 존재하지 않는 코드는 거부된다.
10. 성공한 카드만 팬 컬렉션에 표시되고 카드 상세에서 제작 콘텐츠를 확인한다.

판정: 승인 전 접근 차단, 수량 정확성, 인증번호 유일성, 1회 사용, 팬 컬렉션 반영까지 모두 통과해야 한다.

### 시나리오 C — 권한 격리 및 감사

1. 파트너 A 관리자가 파트너 B의 카드팩을 조회·수정할 수 없어야 한다.
2. 아티스트 스튜디오 사용자는 승인·공개·확률 변경을 실행할 수 없어야 한다.
3. 일반 관리자는 전체 팬 패스와 파트너 운영 기능을 사용할 수 있어야 한다.
4. 루트 관리자만 전체 권한 정책과 운영 계정을 관리할 수 있어야 한다.
5. 카드·확률·발급 배치·인증번호 상태 변경이 감사 로그에 기록되어야 한다.

## 7. 배포 승인 게이트

현재 로컬 검증만으로 배포를 승인하려면 아래 조건을 모두 만족해야 한다.

- [x] 팬 앱과 관리자 웹이 동일한 로컬 백엔드에 연결되어 있다.
- [x] 관리자 로그인과 역할별 권한 검사가 실제 API에서 동작한다.
- [x] 카드 생성 → 검수 요청 → 승인 → 공개 흐름이 데이터베이스에 저장된다.
- [x] 카드팩 생성 → 카드 구성 → 확률 100% 검증 → 새 버전 → 공개 흐름이 동작한다.
- [x] 팬 앱에서 공개된 카드팩과 확률표가 표시된다.
- [x] 카드팩 개봉 결과가 팬 컬렉션과 카드 상세에 반영된다.
- [x] 특별 카드 발급 배치와 고유 인증번호 생성이 동작한다.
- [x] QR/인증번호 등록 성공, 중복 등록 차단, 잘못된 코드 거부를 확인했다.
- [x] 카드 상세가 독립 경로로 동작하고 새로고침·뒤로가기를 통과한다.
- [x] 카드 뒷면 틸트와 카드 제공 데이터 표시를 확인했다.
- [x] 파트너·하위 관리자·스튜디오 사용자 간 권한 격리를 확인했다.
- [x] 발급·등록·확률·권한 변경 감사 로그를 확인했다.
- [x] 프론트엔드 테스트, 백엔드 테스트, 빌드, 린트, 핵심 브라우저 시나리오가 모두 통과했다.

### 현재 판단

최근 로컬 검증에서 카드 상세를 모달에서 독립 화면으로 수정하고, 팬앱의 인증코드 등록·카드팩 개봉·실제 QR 등록부터 컬렉션·상세 확인까지 실제 API와 함께 검증했다. 관리자 카드팩 생성·공개와 신규 QR 발급 배치·PNG 생성도 확인했다. 다만 관리자 카드 이미지 업로드를 포함한 카드 생성·검수·공개 UI 연속 흐름과 운영 환경의 다중 기기 QR 호환성은 별도 검증이 남아 있다.

따라서 Task 10의 자동화·로컬 API 게이트는 `통과`로 기록한다. 다만 관리자 브라우저의 파일 첨부를 포함한 UI 연속 시나리오와 운영 환경 다중 기기 QR 호환성은 아직 수동 검증 범위이므로, 프로덕션 배포 승인은 별도 `검증 보류`로 유지한다.

## 8. 카드 조합

카드팩에서 얻은 중복 카드를 재료로 사용해 상위 등급 카드를 획득하는 기능이다. 특정 카드를 지정해 교환하는 방식이 아니라, 정해진 조건을 충족하면 해당 카드팩 또는 컬렉션 범위 안의 상위 등급 카드가 랜덤으로 결정된다.

### 8.1 기본 규칙

- 조합 대상은 중복 보유 카드이며, 카드 종류와 상관없이 조건에 맞는 수량을 소비한다.
- 조합 결과의 대상 범위는 같은 카드팩 또는 관리자가 설정한 아티스트·컬렉션 범위로 제한한다.
- 결과는 상위 등급 풀에서 랜덤으로 결정한다.
- UR, 시즌 한정, 아티스트 직접 제작 카드 등은 기본적으로 조합 결과 풀에서 제외할 수 있어야 한다.
- 조합에 사용된 카드는 즉시 차감하고 결과 카드를 원자적으로 지급한다.
- 조합 성공·실패·재시도 시 중복 지급이나 재료 복구 오류가 없어야 한다.
- 결과 확률은 조합 화면과 운영자 웹에서 공개한다.
- 조합용 확률표와 일반 카드팩 확률표는 서로 다른 버전·감사 이력으로 관리한다.

조합은 특정 카드를 직접 선택해 얻는 기능이 아니라 상위 등급 풀에서 랜덤으로 보상받는 기능이다. 따라서 조합으로 원하는 카드를 확정적으로 얻을 수 있다고 오해하지 않도록 필요한 중복 수량, 결과 등급, 결과 풀, 확률을 실행 전에 보여준다. 조합이 카드 수집의 의미를 약화시키지 않도록 카드팩·아티스트·시즌 범위를 벗어난 무제한 조합은 제공하지 않는다.

서비스 문구에서는 기능명을 `카드 재조합`, `카드 승급`, `중복 카드 교환` 중 하나로 확정한다. 단순히 `조합`이라고만 표시하면 사용자가 특정 카드 제작 기능으로 오해할 수 있다.

### 8.2 검증 시나리오

1. 팬이 조합 가능한 중복 카드와 필요한 수량을 확인한다.
2. 조합 전에 소비될 카드와 결과 등급 풀·확률을 확인한다.
3. 팬이 조합을 실행한다.
4. 서버가 보유 수량을 다시 확인하고 한 번만 재료를 차감한다.
5. 상위 등급 결과를 발급하고 팬 컬렉션에 저장한다.
6. 새로고침·중복 요청·네트워크 재시도 후에도 결과가 한 번만 존재하는지 확인한다.
7. 조합 이력에 재료, 확률 버전, 결과, 시각을 기록한다.

## 9. 카드 트레이딩

팬 간 카드 소유권을 이전하거나 교환하는 기능이다. 초기 버전은 카드 간 직접 교환보다 안전한 제안·수락 흐름을 우선한다.

### 9.1 기본 흐름

1. 팬이 다른 팬의 공개 컬렉션에서 거래 가능한 카드를 선택한다.
2. 상대 팬에게 원하는 카드와 제공할 카드를 포함한 거래 제안을 보낸다.
3. 상대가 수락하면 양쪽 카드의 소유권을 동시에 이전한다.
4. 한쪽이 카드를 잠금·사용·재료 소비·다른 거래에 등록하면 제안은 자동으로 만료된다.
5. 거절·취소·만료·완료 상태와 양쪽의 거래 이력을 보존한다.

초기 버전에서는 모든 카드의 자유 거래를 허용하지 않는다. 거래 가능한 카드만 별도 정책으로 표시하고, 거래 제안 전에 해당 카드의 거래 가능 여부와 제한 조건을 안내한다.

### 9.2 거래 정책으로 확정해야 할 항목

- 거래 가능 카드와 거래 불가 카드의 기준
- 이벤트·팬 패스·한정 특전·조합 결과 카드의 거래 가능 여부
- 적용 중인 카드, 기간제 카드, 1회성 아이템과 카드 소유권의 관계
- 거래 수수료, 일일 제한, 신고·차단 정책
- 미성년자 보호 및 사기·현금 거래 유도 방지 정책
- 거래 완료 전 양쪽 카드를 잠그는 원자적 처리

다음 카드는 기본적으로 거래 불가 또는 별도 승인 대상으로 둔다.

- 이벤트·팬 패스·시즌 한정 카드
- 아티스트 직접 제작 카드
- 조합 결과 카드
- 기간제·1회성 카드 또는 이미 효과가 적용된 카드

거래 정책은 카드의 희소성과 소유권을 보호하기 위한 제품 규칙이다. 거래 가능 여부는 클라이언트가 임의로 판단하지 않고 서버가 카드 유형과 현재 상태를 기준으로 결정한다.

거래는 클라이언트 상태가 아니라 서버의 소유권 원장으로 처리해야 한다. 동일 카드가 동시에 두 거래에 수락되는 상황, 거래 중 카드팩 개봉이나 조합으로 소비되는 상황을 반드시 경쟁 조건 테스트로 검증한다.

## 10. 팬 팔로잉 및 컬렉션 소셜 기능

팬이 다른 팬을 팔로우하고 공개된 컬렉션을 구경하거나 거래를 제안할 수 있도록 한다.

### 10.1 공개 범위

- 팔로우 여부와 관계없이 공개 컬렉션을 누구에게 보여줄지 설정한다.
- 전체 컬렉션, 특정 아티스트, 특정 카드팩, 보유 수량을 각각 공개·비공개로 설정할 수 있다.
- 인증번호, 거래 상세, 개인 정보, 비공개 카드 콘텐츠는 공개하지 않는다.
- 차단한 팬은 컬렉션 조회·팔로우·거래 제안이 모두 제한된다.

### 10.2 검증 시나리오

1. 팬 A가 팬 B를 팔로우한다.
2. 팬 A가 팬 B의 공개 컬렉션과 카드 상세를 조회한다.
3. 팬 A가 공개된 거래 가능 카드에 거래를 제안한다.
4. 팬 B가 제안을 수락하거나 거절한다.
5. 팬 B가 컬렉션을 비공개로 전환하면 팬 A에게 더 이상 상세가 노출되지 않는다.
6. 차단·언팔로우·거래 취소 후 접근과 알림 상태가 일관되게 바뀐다.

팔로잉은 단순한 컬렉션 탐색 기능이 아니라 거래 제안으로 이어지는 소셜 진입점이다. 따라서 거래 제안 스팸, 원치 않는 컬렉션 노출, 사생활 침해를 막기 위해 공개 범위·알림 제한·차단을 함께 제공한다.

## 11. 아티스트 스튜디오 전문 효과 편집

현재 카드 콘텐츠에 포함된 효과 표현을 확장해, 아티스트가 전문적인 카드 결과물을 만들 수 있는 편집 환경을 제공한다. 효과는 카드 데이터와 분리된 설정으로 저장하되, 승인 시점에 사용된 버전을 고정한다.

### 11.1 효과 편집 범위

- 광원·글로우·반사·홀로그램·포일·입자 효과
- 카드 진입·탭·스와이프·뒤집기·길게 누르기 인터랙션
- 앞면과 뒷면의 독립 효과 설정
- 음성·영상·모션 레이어와 재생 조건
- 손글씨·사인·그림의 위치·크기·투명도·블렌딩
- 희귀도별 기본 프리셋과 아티스트 커스텀 프리셋
- 모바일·태블릿·컴퓨터별 미리보기와 성능 등급
- 접근성용 정적 이미지·무음·모션 감소 대체 표현

전문 편집 기능은 한 번에 모두 공개하지 않고 단계적으로 제공한다.

1. 기본 프리셋 선택
2. 색상·강도·속도 조정
3. 탭·스와이프·뒤집기별 효과 설정
4. 음성·영상·손글씨·사인 추가
5. 고급 레이어·타임라인·블렌딩·입자 편집

초기 스튜디오는 1~4단계에 집중한다. 자유 편집기를 먼저 제공하면 카드 로딩 성능, 기기별 렌더링 차이, 검수 난이도, 접근성 문제가 커질 수 있으므로 5단계 기능은 효과 스키마와 성능 기준이 안정된 뒤 도입한다.

### 11.2 안전한 제작·승인 규칙

- 효과 설정은 스키마 검증을 통과해야 저장된다.
- 스튜디오 사용자는 초안과 검수 요청만 할 수 있고 공개 효과를 직접 바꿀 수 없다.
- 승인된 카드의 효과는 버전으로 고정하며, 수정은 새 버전 검수로 처리한다.
- 과도한 광원·소리·진동·자동 재생은 팬 앱 성능과 접근성 기준을 통과해야 한다.
- 효과가 로드되지 않을 때도 카드 앞면·뒷면과 핵심 정보는 정상 표시되어야 한다.

### 11.3 검증 시나리오

1. 아티스트가 카드 효과를 편집하고 여러 기기 미리보기를 확인한다.
2. 초안을 저장하고 검수를 요청한다.
3. 관리자가 효과·미디어·노출 조건을 검수한다.
4. 승인 후 팬 앱에서 탭·스와이프·뒤집기·카드 상세 진입을 확인한다.
5. 뒷면에는 광원 효과 없이 틸트만 적용되는지 확인한다.
6. 네트워크 지연·미디어 실패·모션 감소 설정에서도 대체 표시가 동작하는지 확인한다.
7. 승인된 카드의 효과 버전과 실제 팬에게 표시된 결과가 일치하는지 확인한다.

## 12. 추가 배포 승인 게이트

위 확장 기능을 실제 서비스에 포함할 때는 기존 배포 게이트에 다음 항목을 추가한다.

- [ ] 조합 재료 차감과 결과 발급이 원자적으로 처리된다.
- [ ] 조합 확률과 결과 이력이 팬·관리자 화면에서 일치한다.
- [x] 거래 수락 시 양쪽 소유권이 동시에 이전된다.
- [ ] 거래 중복 수락·동시 조합·동시 카드팩 개봉을 차단한다.
- [x] 팔로우·공개 범위·차단 정책이 API와 화면에서 일치한다.
- [ ] 스튜디오 효과 스키마와 승인 버전이 저장된다.
- [ ] 승인 전 효과·카드가 팬 앱에 노출되지 않는다.
- [ ] 효과 실패·저사양·접근성 환경에서도 카드 사용이 가능하다.

## 13. 카드 가치와 정책 매트릭스

카드의 가치는 희귀도 하나로만 결정되지 않는다. 다음 요소가 함께 작동하므로 카드 유형별 정책을 명시해야 한다.

| 정책 항목 | 확인할 내용 |
| --- | --- |
| 획득 경로 | 카드팩, 이벤트, 팬 패스, 인증번호, 조합 중 무엇으로 얻는가 |
| 발급 수량 | 제한 수량인가, 발급 순간 생성되는 무제한 카드인가 |
| 확률 | 카드팩 확률 또는 조합 확률이 공개되어 있는가 |
| 조합 | 재료로 소비 가능한가, 조합 결과가 될 수 있는가 |
| 거래 | 팬 간 거래가 가능한가, 별도 승인이 필요한가 |
| 효과 | 음성·영상·모션·사인·이스터에그가 있는가 |
| 기간 | 영구 보유인가, 기간제·1회성인가 |
| 재발급 | 분실·오류·운영 취소 시 재발급 가능한가 |
| 공개 범위 | 전체 공개, 팔로워 공개, 비공개 중 무엇인가 |

이 매트릭스가 없는 상태에서 조합과 거래를 구현하면 희귀 카드의 가치, 카드팩 확률, 이벤트 보상, 아티스트 제작 카드의 특별함이 서로 충돌할 수 있다. 카드 등록 또는 카드팩 구성 단계에서 정책 값을 확정하고, 팬 앱과 관리자 웹이 동일한 값을 사용해야 한다.

## 14. 기능 도입 우선순위

기능은 다음 순서로 도입한다.

1. 카드 조합: 중복 카드 소비와 상위 등급 랜덤 보상
2. 제한적 카드 거래: 거래 가능 카드만 제안·수락
3. 컬렉션 공개와 팔로잉: 공개 범위·차단·알림 제한 포함
4. 아티스트 스튜디오 기본 효과 프리셋
5. 전문 효과 편집기: 레이어·타임라인·블렌딩·입자 편집

각 단계는 이전 단계의 소유권, 확률, 권한, 감사 로그가 안정적으로 검증된 뒤 다음 단계로 진행한다.

## 15. 서비스 완성도를 높이는 필수 기능

카드·카드팩 기능만으로도 핵심 흐름은 만들 수 있지만, 실제 서비스 운영과 팬의 지속적인 사용을 위해서는 신뢰·발견·재방문·안전 기능이 필요하다.

### 15.1 카드 소유권 원장

카드의 발급, 등록, 조합, 거래, 회수 이력을 서버에서 하나의 소유권 원장으로 관리한다.

- 카드별 고유 ID와 현재 소유자
- 획득 경로와 획득 시각
- 발급 확률 버전
- 조합·거래·회수 이력
- 운영자 수정 및 재처리 이력

조합과 거래는 클라이언트 상태가 아닌 이 원장을 기준으로 처리한다. 모든 소유권 변경은 중복 지급·동시 사용·재시도에 안전해야 한다.

### 15.2 알림 센터

팬과 운영자가 중요한 상태 변화를 놓치지 않도록 인앱 알림을 제공한다.

- 카드팩 공개·오픈 결과
- 이벤트 시작·종료
- 팬 패스 보상 획득
- 거래 제안·수락·거절·만료
- 카드 검수 결과
- 새 카드 공개
- QR·인증번호 등록 결과
- 기간제 카드 만료 예정

알림별 수신 설정과 읽음 상태를 관리하며, 거래 제안이나 이벤트 알림은 과도한 반복 발송을 제한한다.

### 15.3 카드 탐색과 컬렉션 관리

카드 수가 증가해도 팬이 원하는 카드를 찾을 수 있도록 다음 조건으로 검색·필터링한다.

- 아티스트, 앨범·시즌, 카드팩, 멤버
- 희귀도, 획득 경로, 거래 가능 여부
- 보유·미보유·중복 상태
- 기간제·한정 카드 여부

팬은 위시리스트와 수집 목표를 만들 수 있다. 특정 카드 찜하기, 카드팩 완성률, 중복 카드 정리 제안, 거래 가능 카드 추천을 제공한다.

### 15.4 신고·차단·콘텐츠 안전

팔로잉·거래·아티스트 스튜디오가 연결되면 안전 기능을 기본 제공한다.

- 팬 계정 차단
- 거래 제안 차단
- 카드 콘텐츠 신고
- 이미지·음성·문구 검수
- 신고 처리 상태와 운영자 감사 로그
- 비공개 컬렉션과 카드 콘텐츠 접근 제한

팬의 인증번호, 개인 정보, 비공개 카드 콘텐츠는 공개 컬렉션이나 팔로잉 화면에 노출하지 않는다.

### 15.5 카드 획득 기록과 상세 콘텐츠

팬이 희귀 카드를 신뢰하고 소장할 수 있도록 카드별 획득 기록을 제공한다.

- 카드팩 개봉
- 이벤트 보상
- 인증번호 등록
- 팬 패스 보상
- 카드 조합
- 팬 간 거래

카드 상세는 카드 보기, 카드 정보, 아티스트 메시지, 음성·영상, 효과, 획득 기록으로 구분해 표시한다. 카드 데이터가 늘어날수록 한 화면에 모든 내용을 쌓지 않고 탭 또는 섹션으로 나눈다.

### 15.6 운영 통계와 이상 감지

관리자 웹은 설정값을 관리하는 화면을 넘어 실제 서비스 결과를 확인할 수 있어야 한다.

- 카드팩 오픈 수
- 희귀도별 실제 발급 비율
- 카드별 보유자·중복 보유자 수
- 조합 이용률
- 거래 제안·성사율
- 인증번호 성공·실패율
- 이벤트별 카드 획득 수
- 카드팩 재고와 한정 카드 잔여 수량

예정 확률과 실제 발급률의 차이, 특정 희귀도 과다 발급, 인증번호 중복 시도, 비정상적인 대량 거래를 관리자에게 알려야 한다.

### 15.7 데이터 내보내기와 복구

운영자는 다음 자료를 조회·내보낼 수 있어야 한다.

- 카드·발급 배치 CSV
- 거래 이력
- 확률표 버전
- 감사 로그
- 카드팩·카드 상태

장애가 발생했을 때 발급 재처리, 오류 카드 보상, 인증번호 상태 복구를 수행할 수 있어야 한다.

## 16. 팬 재방문과 차별화 기능

### 16.1 컬렉션 전시 공간

팬이 수집한 카드를 단순히 보관하는 것을 넘어 자신의 컬렉션을 전시할 수 있게 한다.

- 대표 카드 설정
- 컬렉션 테마
- 아티스트별 전시
- 완성 컬렉션 배지
- 공개 컬렉션 방문과 반응

공개 여부는 팬이 직접 제어하며, 거래 불가·비공개·개인 정보는 전시 화면에 노출하지 않는다.

### 16.2 아티스트 활동 연결

카드 획득을 아티스트의 실제 활동과 연결해 수집 동기를 만든다.

- 컴백 카운트다운 카드
- 라이브 방송 참여 카드
- 게시물·콘텐츠에 숨겨진 카드
- 팬미팅 참석 카드
- 아티스트 메시지 해금
- 시즌 종료 후 특별 리워드

이벤트 조건과 카드 발급 조건은 관리자 웹에서 명시적으로 관리하고, 팬 앱에는 획득 조건과 기간을 오해 없이 표시한다.

## 17. 기능 도입 및 배포 우선순위

기능은 다음 순서로 도입한다.

1. 카드 소유권 원장
2. 인증번호·QR 등록 안정성
3. 역할별 권한·감사 로그
4. 카드 검색·컬렉션 관리
5. 알림 센터
6. 신고·차단·콘텐츠 안전
7. 운영 통계·이상 감지·데이터 복구
8. 카드 조합
9. 제한적 카드 트레이딩
10. 팔로잉·컬렉션 전시
11. 아티스트 스튜디오 기본 효과 프리셋
12. 전문 효과 편집기

각 단계는 이전 단계의 소유권, 확률, 권한, 개인정보 보호, 감사 로그가 실제 로컬 시나리오에서 검증된 뒤 다음 단계로 진행한다.

## 18. 추가 배포 승인 게이트

서비스 완성도 기능을 배포에 포함하려면 다음을 확인한다.

- [ ] 카드 소유권 변경이 단일 서버 원장에 기록된다.
- [ ] 카드 발급·등록·조합·거래 재시도 시 중복 지급이 발생하지 않는다.
- [ ] 알림의 생성·읽음·수신 설정이 저장된다.
- [ ] 카드 검색과 보유·미보유·중복 필터가 실제 데이터와 일치한다.
- [ ] 위시리스트와 수집 목표가 새로고침 후에도 유지된다.
- [x] 차단한 계정의 검색·팔로우·공개 컬렉션·거래 접근이 제한된다.
- [x] 신고가 `report` 유형의 고객센터 운영 큐에 기록되고 운영자 알림으로 연결된다.
- [x] 팬 문의가 관리자 큐에서 답변·상태 전이되고 답변 알림으로 연결된다.
- [x] 실패한 이메일·푸시 전달 작업을 관리자 권한으로 재시도할 수 있고 destination은 응답에 노출하지 않는다.
- [ ] 카드 획득 경로와 확률 버전이 상세 화면에 표시된다.
- [ ] 관리자 통계가 발급·거래·조합 데이터와 일치한다.
- [ ] CSV·감사 로그·복구 절차가 실제로 실행된다.
