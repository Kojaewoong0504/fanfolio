# 팬앱 전체 플로우 감사 및 상점 보수 기록

- 감사일: 2026-08-25
- 범위: 팬앱의 홈·탐색·컬렉션·팬 레벨·팬 프로필·거래·상점 주요 라우트와 관리자 상품 상세 콘텐츠 연결
- 기준: 로컬 팬앱, 현재 로그인된 데모 계정, 프리뷰와 인증 앱 모드의 동작 비교

## 결론

핵심 화면 라우팅과 주요 API 연결은 이미 존재하지만, 상점 일부가 실제 데이터와 목업 데이터를 함께 사용하고 있었다. 그 결과 실제 잔액은 0P인데 상점에는 3,250P가 표시되고, 상품 상세에서 결제 화면을 건너뛰어 주문 API를 바로 호출하는 문제가 확인됐다.

이번 보수에서 상점의 잔액·내역·상품 상세·결제 진입을 실제 앱 데이터 기준으로 정리했다. 현재 계정의 실제 잔액과 주문·교환 내역이 없으면 해당 빈 상태가 표시되는 것이 정상이다.

## 확인된 정상 연결

- 탐색, 팬 찾기, 팬 프로필, 공개 컬렉션, 내 컬렉션, 원하는 카드 등록은 인증 앱 라우트로 연결되어 있다.
- 팬 프로필의 거래 제안은 거래 카드 선택 화면으로 이동하고, 원하는 카드와 내가 보낼 카드를 구분하는 단계가 있다.
- 컬렉션의 원하는 카드 등록은 위시리스트 API를 사용한다.
- 관리자에서 등록한 상품의 `detailContent` 블록은 팬앱 상품 상세에서 텍스트·이미지 블록으로 표시된다.
- 상점 상품 목록과 상품 상세는 카탈로그 API를 사용한다.

## 원인과 조치

### 1. 상점 포인트가 목업 값으로 고정됨

원인: 앱 모드에서도 상점 화면과 내역 요약이 `3,250P`를 직접 표시했다.

조치: 상점과 구매·교환 내역에서 `/me/points`를 호출해 잔액을 표시한다. 로딩 중에는 로딩 상태를, 호출 실패 시에는 오류 상태를, 잔액 0은 실제 0P로 표시한다.

### 2. 구매·교환 내역이 실제 데이터와 분리됨

원인: 주문 API는 호출했지만 구매 요약과 교환 기록은 목업 값으로 남아 있었고, 주문이 없을 때 프리뷰 기록이 섞일 수 있었다.

조치: `/me/shop/orders`의 구매 기록과 `/me/points` 원장의 교환 기록을 앱 모드에서 조합한다. 실제 기록이 없으면 “아직 이용 내역이 없어요” 빈 상태를 표시한다.

### 3. 상품 상세에서 결제 화면이 우회됨

원인: 상품 상세의 구매 버튼이 `POST /me/shop/orders`를 즉시 호출했다.

조치: 상품 상세 구매 버튼은 `/shop/checkout?productId=...`로 이동한다. 결제 화면이 상품과 포인트 잔액을 다시 읽고, 구매 확인 시에만 실제 주문 API를 호출한다. 잔액이 부족하면 주문 버튼을 비활성화하고 안내한다.

### 4. 결제 화면이 고정 상품·고정 결제수단을 사용함

원인: 결제 화면이 Nebula 상품, 1,200P, 3,250P, 네 가지 결제수단을 고정 표시했다.

조치: 앱 모드에서는 URL의 상품 ID로 상품 상세를 읽고 현재 백엔드 계약에 맞춰 포인트 결제만 노출한다. 프리뷰 모드는 디자인 확인을 위해 기존 샘플 결제수단을 유지한다.

## 아직 추가 개발이 필요한 범위

- 현재 백엔드 주문 계약은 포인트 결제만 지원한다. 카드·카카오페이·네이버페이는 실제 PG 연동과 결제 검증이 필요하다.
- 포인트 충전·환불·결제 실패 재시도 정책은 별도 API와 운영 정책이 필요하다.
- `point_item`, `limited_item` 상품은 관리자와 카탈로그 모델에 타입이 있으나 주문 처리·지급 로직을 별도로 확정해야 한다.
- 카드팩 주문 생성 이후 실제 카드팩 개봉·지급 상태를 주문과 연결하는 정책이 필요하다.
- 거래는 현재 단일 데모 계정과 카드 데이터에 의존하므로, 두 계정 간 수락·잠금·완료를 포함한 운영 E2E는 별도 테스트 계정이 필요하다.
