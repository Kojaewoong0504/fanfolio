# 팬앱 UI/UX 시각 감사

- 검사일: 2026-08-25
- 대상: `http://127.0.0.1:5173`
- 범위: 홈, 탐색, 보관함, 팬 레벨, 상점, 팬 찾기, 팬 프로필, 거래 제안, 원하는 카드 등록, 상품 상세, 알림
- 목적: 화면 간 디자인 시스템 일관성, 반응형 셸, 스크롤 동작, 빈 상태와 데이터 상태, 주요 UI/UX 흐름 점검

## 검사 방법

1. 각 라우트를 실제 로컬 브라우저에서 새로 열고 렌더링이 끝난 뒤 DOM 스냅샷과 화면 캡처를 확인했다.
2. `document.documentElement`와 `body`의 실제 스크롤 크기, 화면 너비, 가로 오버플로 요소를 읽었다.
3. 긴 화면은 최상단과 최하단을 모두 확인해 고정 하단 탭이 콘텐츠를 가리는지 점검했다.
4. 캡처는 이 문서와 같은 폴더의 `fan-app-ui-audit-2026-08-25-*.png` 파일로 보관했다.

## 요약

공통 앱 셸은 대부분 `430px` 폭으로 안정적으로 맞고, 홈·탐색·보관함·팬 레벨의 하단 탭도 같은 5개 구조를 사용한다. 핵심 문제는 전체 구조가 무너진 것이 아니라, 특정 상태와 특정 화면에서 공통 규칙이 깨지는 방식이다.

이번 요청의 핵심인 공통 UI 일관성 기준으로 보면 우선순위는 다음과 같다.

1. 스크롤바 유무에 따른 앱 셸의 수평 이동 제거
2. 라우트별 상단 헤더 높이·세로 시작점 통일
3. 알림 화면의 이중 헤더 제거 또는 역할 통합
4. 하단 5탭의 공통 토큰화와 상세 화면 숨김 규칙 문서화
5. 홈의 이벤트 빈 상태, 상점 오버플로, 빈 상태 밀도 정리

## 2026-08-28 P1 재검증 결과

- 알림 화면은 공통 앱 헤더와 하단 5탭을 렌더링하지 않고 `DetailTopBar` 하나만 사용하도록 반영했다. 배포 팬앱 `/notifications`를 단일 브라우저 탭에서 열어 뒤로가기 1개, 알림 제목 1개, 필터 3개만 노출되는 것을 확인했다.
- 세로 스크롤바에 따른 셸 이동은 `scrollbar-gutter: stable`과 브라우저 스크롤바 비표시 규칙으로 고정했다. 공통 셸과 하단 내비게이션은 `430px` 및 `74px` 토큰을 공유한다.
- 주요 탭 헤더·하단 5탭은 공통 geometry contract로 정리했고, 360px 반응형 규칙은 자동 회귀 테스트로 고정했다.
- 홈 이벤트 빈 상태는 배너처럼 보이는 빈 남색 영역 대신 `새로운 이벤트를 준비하고 있어요` 문구와 `이벤트 둘러보기` 행동을 제공한다.
- 팬앱 호스팅 홈과 스튜디오 홈은 같은 브라우저 탭에서 실제 HTTP 화면을 확인했고, 팬앱 알림 화면에는 콘솔 오류가 없었다.

## 발견 사항

### P1 — 알림 화면에 헤더가 두 겹으로 노출됨

- 경로: `/notifications`
- 증거: [알림 캡처](./fan-app-ui-audit-2026-08-25-notifications.png)
- 관찰: 상단에 `FANFOLIO / 알림` 공통 앱 헤더가 있고, 바로 아래에 뒤로가기·`알림`·설정 아이콘을 가진 별도 헤더가 다시 표시된다.
- 문제: 사용자는 어느 헤더가 현재 페이지의 기준인지 판단하기 어렵고, 다른 상세/유틸리티 화면과 헤더 규칙도 달라진다.
- 권장 조치: 알림을 공통 앱 헤더 기반 화면으로 둘지, 집중형 알림 화면으로 둘지 하나로 결정한다. 집중형을 유지한다면 공통 앱 헤더를 숨기고 내부 헤더 하나만 남긴다.

### P1 — 세로 스크롤바 유무에 따라 공통 셸과 공통 요소가 수평 이동함

- 경로: `/home`, `/discover`, `/collection`, `/growth`, `/shop` 및 상세/유틸리티 화면
- 증거: 공통 좌표 측정 결과와 각 화면 캡처
- 측정: 긴 화면 계열에서는 문서 viewport 폭이 `1265px`, 앱 셸이 `x=417.5px`에 놓였고, 짧은 화면 계열에서는 viewport 폭이 `1280px`, 앱 셸이 `x=425px`에 놓였다. 셸 폭은 모두 `430px`로 동일하지만 화면 중앙 기준점이 `7.5px` 달라진다.
- 관찰: 사용자는 화면을 전환할 때 로고·알림·프로필·하단 탭 전체가 좌우로 살짝 이동하는 것으로 느낄 수 있다. 이는 개별 컴포넌트의 좌표가 잘못된 것이 아니라 브라우저 세로 스크롤바가 차지하는 폭을 포함한 `margin:auto` 중앙 정렬이 화면마다 다르게 계산되는 문제다.
- 문제: 사용자가 특히 민감하게 느끼는 상단 프로필/알림 위치와 하단 탭의 좌우 기준선이 라우트마다 바뀐다. 캡처에서는 작은 차이지만 화면 전환 시 누적되어 디자인 시스템이 깨진 인상을 준다.
- 권장 조치: 데스크톱 시연 셸의 기준 폭을 scrollbar 유무와 무관하게 고정한다. 예를 들어 최상위 앱 viewport에 안정적인 scrollbar gutter를 예약하거나, 430px 셸을 고정된 stage 안에 배치하고 body 스크롤은 stage 내부에서만 처리한다. `margin:auto`만으로 화면 중앙을 계산하는 방식을 긴 화면과 짧은 화면에 혼용하지 않는다.

### P1 — 공통 상단 헤더의 높이와 세로 기준선이 라우트마다 달라짐

- 경로: `/home`, `/discover`, `/collection`, `/growth`, `/shop`
- 측정된 공통 헤더: 홈 `y=23, h=44`, 탐색 `y=23, h=53.8`, 보관함 `y=23, h=75.2`, 팬 레벨 `y=19, h=75.2`, 상점 `y=23, h=79.2`.
- 관찰: 알림/프로필 버튼 자체는 주요 탭에서 대체로 `32×32px`, 동일한 x 기준에 놓였지만 헤더 콘텐츠의 높이와 시작점은 화면별 제목·설명·전용 스타일에 따라 달라진다. 특히 팬 레벨은 다른 주요 탭보다 4px 위에서 시작하고, 상점은 전용 헤더 규칙으로 높이가 더 커진다.
- 문제: 로고, 제목, 알림, 프로필이 공통 컴포넌트처럼 보여야 하는데 화면 전환 시 상단 덩어리의 높이와 수직 리듬이 달라진다. 제목/설명 길이 차이와 헤더 레이아웃 차이가 구분되지 않는다.
- 권장 조치: `AppHeader`를 `compact`, `standard`, `detail` 변형으로 명시하고 각 변형의 상단 padding, 최소 높이, 제목 baseline, 액션 버튼 크기를 토큰으로 고정한다. 주요 탭(`/home`, `/discover`, `/collection`, `/growth`, `/shop`)은 같은 `standard` 헤더를 사용하고, 설명이 긴 화면도 헤더 자체의 시작선은 유지한다. 상점 전용 보정값과 360px 미디어쿼리의 중복 덮어쓰기는 하나의 반응형 토큰으로 합친다.

### P1 — 하단 5탭은 구조는 같지만 셸 좌표와 스타일 규칙이 여러 번 덮어씀

- 경로: 주요 탭 5개
- 측정: 다섯 화면 모두 하단 탭은 `w=430px`, `h=74px`, 다섯 항목은 각각 `w=82px`, 아이콘 `23×23px`로 측정되어 기본 구조는 일관적이었다.
- 관찰: 구조 자체는 통과하지만 `frontend/src/App.css`에 `.bottom-nav`, `.nav-item`, `.nav-icon`과 360px 미디어쿼리가 여러 구간에서 반복 정의되어 있다. 초기 정의의 `display:flex`, 이후 정의의 `display:grid`, 서로 다른 padding/min-width 규칙이 순차적으로 덮어쓴다. 상점은 별도로 `.shop-shell .bottom-nav{z-index:5}`를 추가한다.
- 문제: 현재 좌표가 우연히 맞더라도 특정 화면 또는 폭에서 아이콘 크기, 라벨 간격, active 색상, 탭 높이가 쉽게 달라질 수 있다. 특히 상세 화면에서 탭을 숨기는 정책과 주요 탭의 고정 탭 정책이 한눈에 보이지 않는다.
- 권장 조치: 하단 탭을 하나의 컴포넌트/스타일 블록으로 정리하고 `--bottom-nav-height`, `--nav-icon-size`, `--nav-label-size`, `--nav-item-gap`, `--safe-bottom` 토큰을 둔다. 5개 항목은 항상 `grid-template-columns:repeat(5,1fr)`로 유지하며, 상세/플로우 화면은 `bottom-nav: none`을 화면 유형 레벨에서 명시한다. 화면별 z-index 보정은 공통 stacking rule로 흡수한다.

### P2 — 상세 화면의 공통 헤더가 주요 탭과 다른 기준 폭으로 배치됨

- 경로: `/fans`, `/fans/local_demo_collector`, `/trades/new`, `/collection/wishlist`, `/shop/products/shop_product_90b1d69bf223`
- 측정: 팬 찾기·팬 프로필·상품 상세의 뒤로가기 헤더는 대체로 `h=74px`, `w=428px`였고, 원하는 카드 등록은 `h=72px`였다. 거래 제안은 하단 고정 footer를 포함해 셸 중심이 다른 짧은 문서 폭에서 `x=425px`로 측정됐다.
- 관찰: 상세 화면에서 하단 탭을 숨기는 방향은 일관되지만, `social-reference-topbar`, `wishlist-picker-header`, `shop-history-topbar`가 각자 별도 컴포넌트로 존재한다.
- 문제: 공통 뒤로가기 위치, 헤더 높이, 제목 baseline이 화면마다 달라질 여지가 크다. 주요 탭에서 상세로 진입할 때 하단 탭이 사라지는 변화와 함께 헤더까지 바뀌어 전환감이 커진다.
- 권장 조치: 상세 헤더를 하나의 `DetailHeader` 계약으로 통합하고 `title`, `back`, `rightAction`, `variant`만 받도록 한다. 현재 화면별 topbar 이름은 유지하더라도 내부 토큰과 레이아웃은 공유해야 한다.

### P1 — 홈 이벤트 빈 상태가 ‘깨진 배너’처럼 보임

- 경로: `/home`
- 증거: [홈 캡처](./fan-app-ui-audit-2026-08-25-01-home.png)
- 관찰: `추천 이벤트` 영역이 짙은 남색 큰 카드로 렌더링되지만 제목·설명·빈 상태 안내는 보이지 않고 `이벤트 둘러보기` 버튼만 떠 있다.
- 문제: 데이터가 없는 정상 상태가 이미지 로딩 실패 또는 카드 콘텐츠 누락처럼 인식된다. 시각적 면적에 비해 정보가 없어 화면 위계가 무너진다.
- 권장 조치: 이벤트 없음 상태에는 밝은 빈 상태 카드와 안내 문구를 사용하거나, 실제 이벤트가 있을 때만 히어로 배경/어두운 테마를 적용한다.

### P2 — 긴 화면에서 외부 브라우저 스크롤바가 노출됨

- 경로: `/home`, `/discover`, `/collection`, `/growth`, `/fans/local_demo_collector`
- 증거: [홈](./fan-app-ui-audit-2026-08-25-01-home.png), [탐색](./fan-app-ui-audit-2026-08-25-discover.png), [팬 레벨](./fan-app-ui-audit-2026-08-25-growth.png), [팬 프로필](./fan-app-ui-audit-2026-08-25-profile.png)
- 측정: 탐색 `scrollHeight 1141`, 보관함 `1189`, 팬 레벨 `1083`, 팬 프로필 `1366`, 브라우저 viewport `963px`.
- 관찰: 모바일 셸 바깥의 데스크톱 브라우저 우측에 스크롤바가 계속 보인다.
- 문제: 모바일 앱을 데스크톱 브라우저에서 시연할 때 화면 오른쪽에 별도 웹페이지가 있다는 인상을 주며, 페이지별로 스크롤 여부가 달라 보인다.
- 판단: 실제 모바일 기기에서는 OS 스크롤바 정책에 따라 다르게 보일 수 있으므로 기능 버그로 단정하지 않는다. 다만 현재 시연 환경에서는 분명한 시각 불일치다.
- 권장 조치: 데스크톱 시연 셸은 `body` 스크롤을 하나의 앱 스크롤 컨테이너로 통일하고, 필요하면 외부 스크롤바를 숨긴다. 긴 화면은 하단 탭과 안전 영역을 포함한 내부 패딩을 공통 토큰으로 관리한다.

### P2 — 상점 내부 가로 오버플로가 공통 폭 규칙과 충돌할 가능성

- 경로: `/shop`
- 증거: [상점 캡처](./fan-app-ui-audit-2026-08-25-shop.png)
- 측정: `.shop-artist-list`는 실제 콘텐츠 폭 `452px`, 컨테이너 `384px`; `.shop-featured-pack`은 콘텐츠 폭 `396px`, 컨테이너 `384px`.
- 관찰: 관심 아티스트 목록은 가로 스크롤 의도가 보이지만, 추천 카드팩도 컨테이너보다 넓은 값이 측정된다.
- 문제: 추천 카드팩의 그림자·버튼·모서리가 작은 화면에서 잘리거나 오른쪽 여백이 달라질 수 있다. 아티스트 목록의 의도된 carousel overflow와 일반 상품 카드의 우발적 overflow를 구분해야 한다.
- 권장 조치: 아티스트 목록에만 `overflow-x:auto`를 허용하고, 일반 상품 카드에는 `min-width:0; width:100%; box-sizing:border-box`를 적용해 셸 폭을 넘지 않게 한다.

### P2 — 빈 상태 화면의 정보 밀도가 화면별로 크게 다름

- 경로: `/collection/wishlist`, `/notifications`, `/shop`
- 증거: [원하는 카드 등록](./fan-app-ui-audit-2026-08-25-wishlist.png), [알림](./fan-app-ui-audit-2026-08-25-notifications.png), [상점](./fan-app-ui-audit-2026-08-25-shop.png)
- 관찰: 원하는 카드 등록과 알림 화면은 핵심 콘텐츠 아래에 큰 빈 영역이 남는다. 상점은 상품 하나만 표시되고 하단까지 큰 여백이 남는다.
- 문제: 정상적인 초기 상태인지 로딩 실패인지, 다음 행동이 무엇인지 화면마다 인지 난이도가 달라진다.

### P3 — 상세/유틸리티 화면의 내비게이션 정책을 명시할 필요

## 접근성/반응형 위험

- 430px 기준은 안정적이지만 360px 이하 미디어쿼리만 별도로 존재하므로 Galaxy S24 Ultra 등 실제 기기 폭과 브라우저 확대 상태에서 긴 텍스트·버튼을 추가 확인해야 한다.
- 가로 스크롤 영역은 키보드/스크린리더 사용자에게 스크롤 가능 여부가 충분히 전달되는지 확인해야 한다.
- 고정 하단 탭이 있는 화면은 마지막 콘텐츠가 탭 아래에 가려지지 않도록 `safe-area`와 공통 bottom padding을 함께 검증해야 한다.
- 빈 상태와 API 오류 상태가 같은 시각적 무게로 보이지 않도록 상태별 색상·문구·재시도 행동을 분리해야 한다.

## 한계

- 현재 감사는 로컬 브라우저의 기본 데모/인증 상태와 현재 노출된 데이터 기준이다.
- 실제 iOS/Android 기기별 OS 스크롤바, 네트워크 지연 중 skeleton, API 장애 재현은 별도 테스트가 필요하다.
- 결제 PG와 간편결제는 범위에서 제외된 상태이므로 결제 수단의 실제 외부 연동은 평가하지 않았다.
